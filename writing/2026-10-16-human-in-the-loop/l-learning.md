# HITL 的学习解释：把"哪里该弹窗"还原成决策权分配问题

> 材料：《怎么设计 Agent 的 Human-in-the-loop》（抖音 · 王二讲Agent）口播 ASR 转写。
> 关键机制已对照一手来源核对：Claude Code 权限与沙箱文档、Anthropic auto mode 工程博客及其后续生产数据、OpenAI Agents SDK 与 LangGraph 的 HITL 文档、pi 的 security/containerization 文档、独立压测 arXiv:2604.04978（见文末清单）。

## 一、真实问题：弹窗不是控制本身，而是一种有代价的控制

"危险操作前弹窗确认"之所以是错的起手式，不是原则错，而是它默认打断的成本约等于零。真实系统里，人是最贵、也最容易失灵的审查器。Anthropic 2026 年公布的一组对照实验（厂商自测口径）很直白：让开发者手工点击确认，只抓到了 13.6% 的危险命令；auto mode 的分类器拦下了 89%；而且会话越长，人的表现越差。这为"弹窗弹多了人会烦"补上了机制解释：**审查质量随打扰频率和使用时长衰减，被反复打扰训练出来的行为是"随手批准"**。一旦如此，人这一层就不再是安全措施，而是可以被稳定穿过的形式。

所以 HITL 设计是一个有两类错误、两类成本的分配问题：

- **误拦**（该放行的被拦）→ 打扰成本，外加用户改用更松的模式，控制被整体绕过；
- **漏放**（该拦的没拦）→ 不可恢复的损害。

"哪里该弹"的真正含义于是变成：在执行链的哪个位置，把决策权交给谁——模型、静态规则、审查模型、人、还是环境边界——让两类成本都落在可接受范围。目标不是消灭漏放，而是**用合理的打扰预算，把不可恢复的损害挡在门外**。

## 二、干预时点由恢复成本决定：三档分级的因果

材料给出的分级正解（只读直接执行 / 可回滚写操作事后通知 / 不可逆与资金、权限、对外发送操作事前审批）背后是同一个变量：

1. **只读直接执行**——没有状态变更，不存在事后修复问题；
2. **可回滚的写操作，事后通知**——存在"事后检测 + 修复"这条替代路径，可以省掉事前等待，只花通知的钱；
3. **不可逆、涉资金、涉权限、对外发送，事前审批**——事后没有修复路径，唯一可用的时间点就是事前。

资金/权限/对外发送被特别点名，是因为它们的"撤销"牵扯第三方：邮件已发出、对方已看到转账，技术上的回滚不等于事实上的收回——这是恢复成本的极端形式，而不是另一条独立的规则。审批内容必须具体（完整命令、要改的文件、订单金额），原因也在机制里：**人只有拿到能判断的上下文，审批才是真判断，否则只是形式化点击**。

两个材料没说破、但直接决定分级可信度的前提：

- **"撤得回"的判定在消费时点，不在文件类型**。"git 撤回就行"的前提是文件已被版本控制、且改动尚未被执行、部署或被下游消费。删掉未跟踪文件无法用 git 恢复；对脚本、配置、CI 文件的编辑，在被执行之后就不再是简单可逆。生态里的工具恰好在按同一方向打补丁：Claude Code 把 `.git`、`.claude` 这类路径当受保护路径，即使命中 allow 也仍走审批；pi 的沙箱扩展默认 `denyWrite` 覆盖 `.env`、`*.pem`。独立压测还发现，被自动放行的"项目内文件编辑"通道恰恰是状态变更动作的大头（超过三分之一），清理类任务的漏检率在其中最高（对抗性测试口径，不能与生产数据直接并论）。结论：自动放行编辑的信任强度要下调一档。
- **"只读"也要限定范围**。工作目录内的读取放行是有意设计；但读取本身可以是泄露链的一半——"读到凭证"与"发得出去"合起来才构成泄露。所以只读放行必须与网络出口、凭证范围放在一起看。

## 三、把打扰降下来：三层机制与各自的失效模式

材料说"记住授权、规则前置、模型审查"三个都要。按机制拆开看，三者的定位和绕过面各不相同：

**(1) 记住授权：把一次性的人类决定固化为可复核的配置。** 用户选"Yes, and don't ask again"，授权被写进仓库根目录的 `.claude/settings.local.json`，下次同类命令自动命中。机制价值在于**打扰率随使用递减而不是恒定**：每个被记住的决定，都把一个人工节点永久降级为规则节点。代价是这是权限面的单向扩张，所以粒度和生命周期是设计问题：它按仓库 + 命令生效，那么在企业里就要回答"谁批准的、写到哪里、如何吊销、跨环境是否共享"。

**(2) 静态规则：把运行期决定提前到设计期。** 精确机制：`deny → ask → allow` 顺序匹配，先命中者生效，特异性不参与排序，allow 无法给 deny 开例外。但必须修正一个关键理解：**规则匹配的是"模型写出来的命令文本"，不是程序的真实效果**。`Bash(git push *)` 挡不住写成 `git -C . push` 的推送；`rm -rf` 换个路径写法、包进脚本（`bash cleanup.sh`）、或经由另一个写文件的工具达成同样删除，都可以不命中规则。官方文档自己把它定性为"对模型常见写法的护栏，不是围绕程序的安全边界"。也就是说它是**概率护栏**——这与材料自己的结论（安全来自边界）一致，只与"写进 deny 就永远执行不了"的绝对化说法冲突。

**(3) 分类器审查：处理规则判断不了的部分（shell 命令、网络请求、项目目录外操作）。** 结构是两级级联：第一级只输出一个 token、不推理、被调成"偏向拦截"（宁误拦勿漏放）；只有被第一级标记的才进入第二级做推理。两级提示词几乎相同、只换最后一句指令，第二级的成本接近缓存命中——这是"把便宜的高召回粗筛与昂贵的精判分离"的标准级联，机制上就是选精度/召回权衡曲线上的一个部署点。

数字要读双边账：第一级误报 8.5%，全流程压到 0.4%——这一侧口径用对了（为"少打扰"服务）；但同一张表里，全流程对真实"过度主动"动作的漏放是 17%，对合成外泄任务漏 5.7%。官方对 17% 的归因值得记住：多数漏检不是没看出动作危险，而是**误判了用户授权覆盖的范围**（把"清理一下 PR"读成了对 force-push 的授权）。所以正确的信任定级是：分类器把打扰降到很低、也拦下大量危险动作，但漏检非零，且它完全不覆盖"项目内文件编辑"这条被直接放行的通道——高风险动作仍需沙箱和审批兜底。

两个容易理解的细节也要摆正：

- **分类器的输入不看工具返回结果，保护的是审查者通道本身**——防止网页、文件里的恶意指令反过来操纵分类器。这不等于 agent 对注入免疫：工具结果本来就会进入模型的上下文（否则"被拦的操作作为工具结果返回、让模型换个做法"这条机制就不成立）。对 agent 的注入防线在输入侧探针与能力边界，不在分类器。
- **失败升级是一道断路器**：连续被拒 3 次或累计 20 次，agent 停下来交给人；无头场景（没有人可问）则直接终止。它防止模型在"此路不通"时无限换姿势、把预算耗在墙上——"没人可问 = 拒绝"这个默认，后文还会再出现。

## 四、等待人：不是并发问题，而是持久化问题

在 agent loop 里 sleep 等回复的方案有一个结构性缺陷：任务寿命被绑在进程寿命上。审批可能等几分钟，也可能等到第二天；服务一重启，任务就没了，还白白占着资源。

正确结构是把"未完成的执行"序列化、退出等待、事后恢复。两个框架给出两种切分粒度：

- **OpenAI Agents SDK**：审批声明在工具上（`needs_approval`，可为常量或按调用判定的函数）。暂停时 `interruptions` 列出待批的 `ToolApprovalItem`（含 agent 名、工具名、参数）；`result.to_state()` 得到 `RunState`，`to_json` 持久化；恢复时取回、`approve`/`reject`、再用 `Runner.run(agent, state)` 从原处继续。可以直接在状态上做"粘性决定"（本次运行内对该工具始终批准/拒绝），批准面是 run 级的（即使审批来自 handoff 或嵌套子 agent，也在最外层统一处理）。
- **LangGraph**：节点内调用 `interrupt()`，整图状态写进 checkpointer；用 `Command(resume=值)` 恢复，resume 值就是 `interrupt()` 的返回值。

**核心陷阱，也是全材料最可迁移的工程原理**：LangGraph 恢复时不是从 `interrupt` 那一行继续，而是**把整个节点从头重放**——因为它的检查点粒度是节点/超步，不是程序计数器。于是 `interrupt` 之前的副作用会再执行一次：先扣款再询问，恢复后就会再扣一次。文档给出的三条对策：用幂等操作（upsert 而非 insert）、把副作用移到 `interrupt` 之后、或拆进独立节点；子图里同名问题会叠加（父节点与子图节点都会重放）。把它抽象出来：**任何"暂停-恢复"边界都是一条重放边界，除非运行时提供程序计数器级快照；写暂停点之前，先问这段逻辑重放一次会怎样。**

企业场景还有两个材料没有、但官方文档已经点出的迁移点：

- **恢复入口本身是安全面**。文档明确 `RunState` 的序列化快照不做身份认证：只能从可信存储恢复，决定必须校验为服务器侧待批项，并发/重放提交要用原子占有检查——否则"伪造或重放的批准"会成为新的漏洞类别。
- **无人应答时 fail closed**。pi 给扩展显式提供 `hasUI` 信号，其 permission-gate 示例的姿态是：有 UI 才询问，没有 UI 就按拒绝处理——"没有人回答的审批等于拒绝"，而不是超时放宽。

## 五、没有人时：边界替代审批——门与墙

审批是**决策时刻的门**，隔离是**设计时刻的墙**。门可以被绕过——换命令写法、换执行通道、用注入让 agent 自己写脚本；墙不能被绕过——沙箱里的 agent 无论怎么写命令，够不到的文件、凭证、进程、网络就是够不到。材料最后一段（"真正的安全来自限制 agent 能访问的文件、凭证、进程和网络"，推荐放进容器或微型虚拟机）说的正是这件事：全自动场景里没有决策可做，安全只能来自能力上限。

两者甚至可以在机制层面互相替代：Claude Code 文档明确，启用沙箱后，受沙箱约束的 Bash 命令可以免询问——"沙箱边界替代了权限提示"。由此得到一个统一的设计准则：**沙箱越强，需要问人的地方越少；反过来，为了让体验不被打碎而把审批调松，就必须把边界收紧——审批的松弛度和隔离的强度是同一个旋钮的两端**。这也解释了材料末段那个 agent 的立场：它默认不做逐步审批，把安全责任整体外置给 OS/容器/微虚拟机边界，需要拦截时用 Permission Gate 扩展在少数命令前补一个门，再加沙箱、白名单与事后审计。按其细节（Permission Gate 示例扩展、容器/微虚拟机建议、`rm -rf`/`sudo` 模式）可确认它指的是 **pi coding agent**——它的 security 文档可以独立核实。

材料里"我都是直接给最大权限"这句话要挂上前提：官方立场是跳过全部审批只建议用于隔离环境；这句口播与前后的容器建议之间没有衔接，容易被二次传播裁成"建议梭哈"。

最后，审计的定位是补偿控制：既然事前防不住全部，就要让事后"查得清、归得因"。能力边界划到哪里，安全主张就到哪里——连 pi 的文档都明确声明，注入攻击与无内置沙箱属于"边界之外的预期风险"，不做承诺。

## 六、整合：一个可复述的心智模型

把全部机制压到最少：

1. **先定墙，再定门。** agent 能触达的文件、凭证、进程、网络决定了伤害的上限，是所有门失效后的兜底；审批只负责在边界之外再减一层概率。
2. **门的时点由恢复成本决定。** 撤不回的操作等人点头；撤得回的操作事后通知。判断"可逆"要问：在哪个时点被消费、由谁恢复、代价多大。
3. **把判断类型匹配给判断者。** 规则判"写法"，分类器判"上下文与授权范围"，人判"意图"。减少打扰的三层机制（记忆授权 → 静态规则 → 分类器）本质是把可以降级的判断逐层从人手里拿走，只把人留在"只有人能判、且判错不可恢复"的位置上——同时清楚每层各自的绕过面。
4. **等待人是持久化问题。** 状态序列化、退出、恢复；暂停点之前保持幂等或无副作用；恢复入口做认证与防重放。
5. **两个指标一起看。** 误拦（打扰）与漏放（风险）必须同时报告，只报一侧的系统无法做信任定级；无人工位时 fail closed。

材料结尾那句"撤不回的操作等人点头，撤得回的操作交给规则和沙箱"正是 2 + 1 的压缩版；掌握后应补的一句是：**每一层都只降低概率，上限由墙决定**。

## 七、材料的视角边界（迁移时会撞上的）

- **单用户 coding agent 语境**。这里的审批者就是操作者本人；企业里审批是角色的、跨人的（谁有权批、双人复核、金额阈值路由），"记住授权"也必须从个人偏好变成受治理、可吊销的策略对象。材料完全没有涉及这层。
- **"修改"路径只有定义没有展开**。定义提到"批准、修改或拒绝"，正文只讲了批准/拒绝。机制上两条路都通：LangGraph 的 resume 值可以是任意 JSON（比如修改后的参数或计划），Agents SDK 的 interruption 携带参数、拒绝时还能给模型带一条说明消息。但"如何让人高效地编辑一次工具调用"，是交互设计与建模问题，超出了材料。
- **两套风险数字不可比**。分类器 17% 的漏放是厂商对真实"过度主动"动作的评估口径；压测的 81% 是刻意构造的模糊授权场景（对抗性口径）。能支持的结论不是"分类器不行"，而是"漏检非零、且集中在特定通道（如项目内编辑）"。
- **分级没有给调参方法**。频率会改变结论：高频、低危、可逆的操作逐个通知同样会把审查质量毁掉。"记住授权"和静态规则实际上是把高频操作从人工队列里剔除，但材料没给"何时该把一档操作降级为规则"的判据。

如果要继续深入，值得按顺序读三份一手材料：Anthropic 的 auto mode 工程博客（看清双边指标表与两阶段设计初衷）、LangGraph interrupts 文档（重放语义与幂等规则）、OpenAI Agents SDK 的 HITL 指南（状态序列化与恢复的安全要求）。再拿一个自己正在设计的 agent，列出它的每个状态变更动作，逐一回答"被谁、在何时消费，恢复代价多大"——分级自然就出来了。
