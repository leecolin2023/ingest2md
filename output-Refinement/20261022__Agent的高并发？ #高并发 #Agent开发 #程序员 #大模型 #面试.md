#### 为什么 Agent 面试不怎么聊传统的高并发？

Agent 面试为什么几乎不聊高并发？因为在很多 Agent 系统里，真正的性能瓶颈，首先卡在大模型的输出端，还没轮到后端业务服务器和数据库承受压力。

很多同学准备秋招、春招，简历上都会写一个自己做的大模型 Agent 项目。但一到面试，面试官问“这个系统怎么扛住大流量”，不少人就习惯性套用传统后端的八股文：Redis 缓存、消息队列削峰填谷、负载均衡支撑几万 QPS。

这时面试官可能反问你一句：**你算过底层调用的大模型，一秒钟究竟能处理几个请求吗？** 这一问，很多同学就懵了。

我是小哲，点赞、收藏、加关注，我们马上开始。想系统学习 AI 开发的同学也可以看一下橱窗。

我打个生活化的比方。传统互联网的高并发，就像高速公路上的自动收费站：一辆车开过去，刷一下卡，几毫秒就放行。传统后端要操心的是把路修宽、增加收费窗口，让一秒钟有几万台车通过。

但大模型 Agent 应用更像是请一位老画家现场画定制油画：画完一版你不满意，还得擦掉重画三四遍。老画家只有一根画笔，一笔一笔画完，可能要花好几分钟。

这时，你就算在工作室门口修一条有一百条车道的高速公路，建一万个排队叫号机，能让画家画得更快吗？当然不能。

这就是我为什么认为：在很多 Agent 应用里，单纯追求传统业务层的几万 QPS，并没有抓住主要矛盾。

看到这里，已经超越 80% 的同学了，可以在弹幕发个“1”，让我看到你。

#### 推理为什么慢：Prefill、Decode 和显存带宽

大模型处理请求，可以分成两个阶段：**读题**和**答题**。

第一阶段叫 **Prefill（预填充）**。你发过来一大段提示词，模型可以并行处理这些输入 token，交给 GPU 做矩阵运算。GPU 擅长并行计算，所以这个阶段通常比较容易发挥计算能力。

第二阶段叫 **Decode（解码）**，也就是生成回答。模型采用自回归生成机制：不能把整段回答一次性生成出来，而是一个 token 接着一个 token 地输出，后一步要依赖前一步的结果。

用大白话讲，就像玩成语接龙。而且模型每生成一步，都要执行计算、读取相应的数据。视频用一个比方来形容：厨师每切一片葱花，都要去仓库搬一趟锅碗瓢盆和调料，搬来搬去比真正切菜还费时间。

在这类场景下，GPU 的计算单元未必一直忙着算，反倒可能主要在等待显存数据搬运，这就是常说的**显存带宽瓶颈**，也叫“内存墙”。

工程师后来用 **KV Cache** 来避免重复计算，把此前计算得到的相关历史信息缓存到显存里，减少不必要的重复工作。

但代价是：每个请求的上下文都要占用一定的 KV Cache 显存。并发请求多起来，显存很快就吃紧。

所以视频认为，在一定硬件和模型条件下，单个模型实例的并发处理能力可能只有十几个、几十个请求，和传统互联网动不动几万并发的场景，关注点很不一样。

看到这里，已经超越 90% 的同学了，可以在弹幕发个“2”。

#### 为什么 Agent 又进一步放大了瓶颈？

普通聊天经常是一问一答：你问一句，模型输出一段话，这次交互就结束了。

Agent 不一样，它通常包含规划、工具调用、观察结果和进一步反思。

举个例子：用户在前端点击一下，让 Agent 查今天的行业新闻，再写一份分析报告。

这个请求进入后端以后，Agent 先调用一次大模型，思考怎么拆解任务，这是第一轮生成。接着调用搜索工具，把找到的网页内容放回上下文，再调用大模型提炼重点，这是第二轮。它可能又发现某个数据不对，继续调用工具、重新检查，然后再生成第三轮、第四轮的结果。

这里有两个让延迟不断放大的问题。

**第一个是串行依赖。** 后一步需要先知道前一步的结果，所以存在依赖的模型调用不能简单地全部并行执行。前面的结果没出来，后续相关步骤就无法继续。

**第二个是上下文滚雪球。** 随着工具调用、观察和反思不断增加，历史内容越来越多。后续模型调用可能需要处理更多 token，占用更多显存，推理延迟也可能继续扩大。

从用户角度看，他只发了一个请求；但这个请求在后端可能持续一两分钟。在这段时间里，业务服务器的大量工作就是等待远端模型 API 或 GPU 集群返回结果。

如果是自建模型，也要考虑 GPU 吞吐能力；如果调用商业大模型 API，则可能碰到每分钟 token 配额等限制。复杂 Agent 任务多起来，模型侧可能先触发限流，而数据库和业务服务器还远没有达到瓶颈。

看到这里，已经超越 99% 的同学了。Offer 离你不远了，可以在弹幕发一个“offer”。

#### 优化方向一：全链路异步与流式传输

那面试时被问到 Agent 系统怎么优化性能和吞吐量，究竟应该答什么？

先从**网络与通信层**讲起，核心是全链路异步化和流式传输。

假设一个请求要等一两分钟。如果采用同步阻塞方式，让每个等待请求都长期占住一个工作线程，那么几百个请求一进来，线程池就可能被耗尽。

所以 Agent 后端可以采用**异步协程 + SSE 流式推送**。等待模型结果时，服务端不必让业务工作线程一直阻塞；模型有新内容生成，就逐步推送给前端。

这样既能利用较少的业务服务器资源维持大量等待中的连接，也能让用户更早看见输出，缓解长时间等待带来的焦虑。

#### 优化方向二：缓存、大小模型路由和并行编排

再看**架构与编排层**。核心思想是：尽量减少不必要的大模型调用，别让旗舰模型干所有事情。

首先可以考虑**语义缓存**。新用户的问题如果和之前处理过的问题意思相近，而且结果允许复用，就从缓存或向量检索系统中返回现成结果，不必再次唤醒大模型。

其次是**大小模型协同路由**。意图分类、格式提取等相对简单的任务，可以交给速度快、成本低的小模型；复杂逻辑推理再交给能力更强的主模型。

另外，设计 Agent 工作流时，要识别哪些子任务确实没有先后依赖。能并行处理的就拆成并行分支，不要让所有事情都机械地串行执行。

#### 优化方向三：按 token 管理容量，准备限流与降级

另一个重要方向，是把传统的按请求数限流，进一步扩展到**按 token 消耗量管理容量**，配合异步任务队列。

因为两个请求的消耗可能完全不一样。一次复杂的深度研究任务，消耗的模型算力可能相当于许多次简单的打招呼请求。只统计每秒进来多少个请求，并不能完整反映模型侧负载。

因此可以在网关层预估 token 消耗，设计相应的令牌桶或配额控制；同时配置不同厂商、不同模型的接口，根据可用性和负载做路由、故障降级。当主模型接口出现问题时，尽可能切换到备用方案。

#### 面试时怎样串起这套逻辑？

只要抓住**自回归生成耗时**和**显存带宽受限**这两类底层问题，很多面试变形题就比较容易回答。

比如面试官问：开发一个 AI 原生应用，和开发传统微服务架构有什么本质区别？或者让你现场设计一个企业级大模型网关，最需要关注哪些指标？

不要一上来就背数据库分库分表。可以先说明：传统后端常关心短平快请求下的 CPU、数据库和磁盘读写；大模型应用则要额外关注长时间等待时的连接管理、上下文增长引起的显存与吞吐压力，以及 Agent 多轮串行调用放大的延迟。

然后顺着这些矛盾提出组合方案：**异步流式处理长连接、语义缓存和大小模型路由减少推理开销、并行编排缩短无谓串行时间、token 级限流与故障降级维持稳定性**。

这样讲，面试官至少能看出来，你关注的是大模型工程化的实际瓶颈，而不是只会调接口、拼一个玩具项目。
