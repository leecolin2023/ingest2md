### 00:00–04:49

去大厂面试 RAG 或 Agent 工程师，面试官很可能会问：做混合检索，为什么要把 BM25 和向量检索配合使用？两路各召回多少条，再交给 Reranker 才合理？

如果回答“BM25 找关键词，向量检索找语义，两路各取 100 条直接扔给 Reranker”，就很像背八股文，未必能体现真实项目调优的经验。大家好，我是阿星。想系统学习大模型的同学，可以看看我整理的大模型面试资料和学习路线图，今天先把这个问题讲清楚。

**第一，为什么不能只依赖一种检索？**

有些人觉得有了向量检索，传统的 BM25 就可以丢掉。其实不是这样。只用向量检索时，如果遇到精确型号，例如“iPhone 15 256GB 黑色”，或者行业缩写、专业黑话，向量库可能召回语义上相似、但具体型号不对的结果。

反过来，只用 BM25 遇到同义词和不同表述，也容易漏召。例如用户问“怎么修空调”，文档写“空调不制冷怎么办”，字面上不一定完全重合，就可能错过重要内容。BM25 擅长精确字面匹配，向量检索擅长语义泛化；两路结合，才能扩大检索覆盖。

**第二，两路到底各召回多少条？**

作者建议从三个步骤推演。

第一步，先计算 Reranker 的处理上限。影响召回数量的不只是检索能力，更是下游精排能否承受。作者以一个 Base 级重排模型作示例，假设单次推理延迟在 20～50 毫秒左右。如果两路各召回 1000 条，合起来 2000 条，全交给重排进行交叉注意力计算，计算量和显存占用就可能明显上升，重排环节甚至可能耗费 6～15 秒。

因此，作者提出，在高并发线上系统里，为了平衡延迟和效果，可以把进入重排的候选总数控制在 200～500 条，例如以 300 条作为示例预算。

第二步，将候选额度分配给 BM25 和向量检索。BM25 计算轻、速度快、可解释性强，可以作为精确检索的保底通道。作者举例，BM25 先取约 200 条，向量检索取约 150 条，也可以取 200 条。假设两路分别取 200 和 150 条，那么合并前约有 350 条候选。

第三步，合并去重。两路结果不能直接全塞给 Reranker，应该先按文档 ID 去重，而不是按照召回分数去重。两路合并的 350 条候选，可能去重后剩下约 300 条，再把这个较干净的候选集交给 Reranker。

这样的回答路径就是：**先考虑计算预算，再分配两路候选，最后合并去重，进入重排。** 作者认为，相比直接报一个固定 Top-K，这样更能体现工程设计思路。

最后留一道追问：BM25 的原始得分和向量检索的相似度分数并不在同一个尺度上，合并之后，除了按文档 ID 去重，该怎么做初步融合？例如 RRF（倒数排名融合）应该怎样使用？有兴趣可以在评论区讨论，也可以试着动手改造自己的 RAG 检索链路。
