意图识别，你自己说哪一场 Agent 的面试不问，想拿 20K offer 这个问题你得答明白。这套回答你可能还没听过，我是小哲，点赞收藏加关注，我们马上开始。想系统学习 Agent 开发的同学可以查看橱窗的系统课哦。首先，意图识别业内常见的方案有 4 种。**第一种：结构化 Function Call**

第一种叫结构化 Function Call，什么意思？我举个例子：你可能觉得这东西怎么看起来有点像工具调用啊。

没错，工具调用就是意图识别的一种。假设你有两个工具，一个查天气。一个做菜。用户问：请帮我查一下北京今天的天气是什么。好，那大模型是不是就会从你塞给大模型上下文的工具中去选择查天气，这叫不叫识别意图？同时还把参数填充给工具，北京5月8号，然后工具返回今天的天气是什么。因此，结构化就体现在大模型还会直接帮你把参数填充好，所以记住第一个结论：工具调用就是意图识别的一种。**第二种：提示词分类**

第二种方式，提示词分类。

举个例子，假如你要做个酒店 Agent。那酒店它有哪些能力啊，什么退房。订房、洗衣服、吃饭等等一二十种。那客户问：请帮我订个房。那么这个时候大模型的上下文就有用户的提问，请帮我订个房，然后再加上所有的能力范围。你会把这些所有能力都塞给大模型。你告诉大模型啊，我们的这个 Agent 有这么多的能力，然后它会意图识别出来，用户是想要订房，接下来去调用子 Agent。

也就是说我们的每一个子 Agent 分别对应一项能力，这也是业内非常普遍的做法。我订房就走订房的 Agent，我退房就走退房的 Agent，这就叫解耦。好，我们再来看第三种叫： **第三种：RAG 分类**

RAG 分类。RAG 分类一般用于什么场景呢？假设我们有一个非常大型的客服，很大很大的系统跟淘宝一样大。那可能这个系统的能力范围非常广，有几百种怎么办？我还能用前面的这种方式吗？把所有的能力都塞给提示词吗？

不可以吧，这上下文太长了。所以这个时候我们可以借助 RAG 检索。我举个例子，用户问：请帮我查一下这个订单物流到哪里了。好，通过 RAG 的语义检索去召回相似度最高的 Top K，这时剩下三条：一个订单查询，一个物流，一个数码 3C，然后大模型去决策：哦，原来你是要查物流，然后去走物流 Agent 去查询这个订单的物流信息。到这里你发现没有？二和三，它在做什么事情呢？

它既是意图识别又是路由啊。其实意图识别和路由是两个概念，就跟你开车一样，要导航：我要去湖北省武汉市，我要去湖南长沙，全国那么多城市，你哪里记得住呢？所以你先是一级的省份，二级的城市，三级的县城，这跟我们讲的二和三是不是一个道理？提示词分类就属于一级路由，退房、 订房、洗衣服、吃饭叫一级啊，最后筛选出来，我们就是订房。那 RAG 分类呢，二级路由。

你看我前面有几百种，我通过 RAG 检索去进行筛选，筛选之后只剩下几条相似度最高的，这叫二级。接着把二级路由筛选完的精简内容丢给大模型的上下文。这个时候上下文是不是就不会被撑爆了。最后返回用户的真实意图。所以二和三的明确定义，它叫意图识别加路由。我们再来看**第四种：模型微调**

第四种叫模型微调。意图识别其实也可以单独训练一个模型来进行微调。微调提供哪些数据呢？全部都是这种数据。

对呀，我要干个什么什么，意图是什么啊？我要吃饭，意图是吃饭；我要洗澡，意图是洗澡。给大量的这种数据让模型去训练，最后训练出一个专门用于意图识别的模型。那么每次用户提问，先经过我们的意图识别模型，得知用户意图之后再去调什么 子 Agent。那什么情况下会用模型微调呢？其实它有它独特的优势。前三种方案常会调用模型或检索服务，如果业务场景需要调用本地模型，模型微调是不是就派上用场啊？

我可以在本地进行意图识别。再根据业务要求评估性能，所以，再被问到，意图识别不能只给一个定义，要把工具调用、提示词分类、RAG 分类和模型微调讲清楚，并说明各自的适用场景，以及它们和路由之间的关系。
