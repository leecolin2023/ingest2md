## 转写正文

### 00:00–05:00

做 Rerank 的同学经常会遇到一个问题：现在的向量模型越来越强，为什么还要保留传统的 BM25？很多人回答“BM25 负责关键词，向量检索负责语义，两路各取 100 条，再全部交给 Rerank”。这个方案做 Demo 或许可以，但上线后很容易出问题。候选取少了，可能漏掉证据；取多了，又会拉高 Rerank 延迟、GPU 压力和成本。真正要设计的是**召回覆盖、精排预算、线上延迟三者之间的平衡**。

为什么不能只用向量检索？向量擅长语义理解，但不一定擅长精确字符串匹配。比如搜 RTX 4090、订单号、药品名、错误码，向量检索可能找回显卡对比或安装程序，却漏掉完全符合型号的商品，这就是语义漂移。

反过来，只用 BM25 也不够。用户搜“省钱攻略”，文档写的是“节约技巧”，字面重合很少，BM25 可能漏召，但向量模型可以判断两种说法语义相近。所以分工是：BM25 负责硬匹配，守住精确查询的下限；向量检索负责软匹配，扩大语义召回的上限。

**第一步，先确定精排总预算。**两路各自召回多少，不能先随手定数字，而应该从下游 Reranker 能处理多少候选推算。重排通常使用交叉编码器，让 Query 和每个候选文档进行深度交互，候选越多，计算量和推理延迟就越大。如果 BM25 和向量检索各取 500 条，把 1000 条全部交给 Rerank，可能使 GPU 负载升高、延迟飙升，甚至请求超时。

因此，先根据模型、文档长度、预处理、CPU、并发量和目标 P95 延迟进行压测，找到候选总预算。假如测试发现去重后 200 条候选可以满足延迟目标，那么就以 200 条作为当前精排预算。召回通道可以扩展，但进入精排阶段的规模必须受控。

**第二步，按 Query 类型分配两路候选额度。**订单号、产品型号、药品名、错误码等强精确查询，可提高 BM25 份额；口语化问题、同义表达、上下文指代等，可以提高向量检索份额。对比分析和多跳问题，可以适当扩展候选数量，也可以把问题拆成多个子问题检索。更合理的做法不是固定 BM25 取 200 条、向量取 150 条，而是先设总预算，再动态分配额度。

**第三步，合并去重。**同一份文档可能同时被 BM25 和向量检索召回。去重应该基于文档 ID，并且保留它来自哪些通道、在各通道的排名和原始分数等信息。这样既避免重复精排，也能利用多通道命中信息。去掉的是重复文档，不是独立证据。

**第四步，用 RRF 等方法融合排序。**BM25 分数和向量相似度不在同一个尺度，不能直接相加。可以分别归一化后加权，也可以采用 RRF（倒数排名融合）。RRF 不比较原始分数，而是根据文档在各条召回通道中的名次计算分数。常见单通道贡献形式为：

`1 / (k + rank)`

其中 k 是平滑常数，工程里经常以 60 作为初始值，但仍须通过评测确认。一个文档如果在两路都排名靠前，融合得分通常也更高。RRF 可以作为混合检索的初始基线，积累了标注、点击和答案采纳数据后，还可以探索 Learning to Rank。

### 05:00–07:23

面试官还可能继续追问四个问题。

**第一，怎样判断 Query 更适合 BM25 还是向量？**可以识别订单号、型号、错误码和专有名词等强词法信号，也可以判断问题是否口语化、是否存在指代、是否需要语义扩展。但不要过早只保留一路；生产系统里仍可以混合召回，再动态调整额度和权重。

**第二，去重后候选不够预算怎么办？**可以从两路召回列表后续名次中补位，直到达到预算或者相关性阈值。不过不能为了凑数量，引入无权限或低质量内容。

**第三，已有 Rerank，为什么还要 RRF？**RRF 做轻量的初步融合，Rerank 则做成本较高的深度判断。先用 RRF 形成初始顺序，可以控制后续精排规模。当然，如果候选本来就很少，也可以去重后直接精排。

**第四，最终候选预算怎样确定？**先用 Golden Data Set 观察候选量与 Recall@K 的关系，再压测 Rerank 的 P50、P95 延迟、吞吐和 GPU 利用率。最后比较端到端正确性、Token 成本和任务完成率，选择质量收益逐渐变缓、而延迟仍满足 SLA 的那个拐点。

所以，混合检索不是把 BM25 与向量召回简单拼接。BM25 管精确匹配，向量管语义覆盖，RRF 管初步融合，Rerank 管精排；候选预算则决定方案能否稳定上线。可以回头检查自己的系统：两路 Top-K 是按 Query 类型动态决定的，还是上线时随手写死后就再没调整过？
