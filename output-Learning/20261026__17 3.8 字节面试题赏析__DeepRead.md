# 字节 AI 面试题赏析：缓存、动态路由与线上评测

> 原稿：`output/20261026__17 3.8 字节面试题赏析/content.md`（39:02）；Deep Read V6.4，Cognitive-Synthesis。

## 第一组追问：检索内容变化，前缀缓存还有意义吗？

讲师从“固定检索片段的排序、合并以触发前缀缓存”切入，先区分 KV Cache 与跨请求复用的 Prefix Cache。他的解释是：模型计算 token 的键值向量会产生缓存，而前缀缓存尝试把多个请求共享的起始部分复用。检索切片顺序不稳定会减少公共前缀，因此他提出三种做法：同一批切片尽可能稳定排序；高频、较固定的问答放到较前方的提示词中；提示词按“稳定部分→低频变化→高频变化”组织。

他进一步解释：缓存不是非全即无。即使动态检索结果无法命中，之前共同的提示词部分仍有复用可能；作用在于减少重复预填充开销并改善首 token 延迟。材料没有给出实际命中率或性能实验。

## 第二组追问：Redis 在 AI 客服中究竟缓存什么？

讲师把模型内部 KV/前缀缓存与业务侧的 Redis 缓存作对照：Redis 可以保存高频问题的回答，重复问题先查缓存，未命中才调用模型。由此产生“不同问法是否表示相同意图”的新问题。他建议将问题向量化做语义相似度匹配，必要时让一个小模型再次判断两个问题是否真正等价，并通过用户反馈发现误命中。

“我想办理贷款”和“我想查询贷款”是他用来说明高相似不代表可共享答案的例子。他同时比较向量数据库与封装了 embedding、存储、检索过程的托管知识库，并提到平台知识库的便利性。

## 第三组追问：动态路由是否真的动态？

面对“根据用户 query 如何决定模型”的问题，讲师援引 LangChain 中按上下文或用户等级选择模型的机制。他尤其强调不要给面试官一个无法自证的“简单问题给小模型、复杂问题给大模型”口号。接下来的追问逐步转向：路由意图判断错误怎么办、线上 bad case 如何发现、不同模型与提示词变更如何控制风险。讲师把离线评测集、轨迹评估、监控和兜底串联为回答线索。

## 材料的统一组织

三组题表面分别涉及模型缓存、Redis 与路由，本质都是要求候选人说明：**一种优化如何工作、在变化的真实输入下为何仍有效，以及失败时如何观测和修复。** 讲师建议先说清概念，展示知识面，再正面回答追问；他的讲述大量采用课堂回忆和口语例子，而非严格技术说明。
