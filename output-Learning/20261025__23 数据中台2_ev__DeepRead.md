# Deep Read｜同一套原始聊天为何要清洗出不同业务数据

> 来源：`output/20261025__23 数据中台2_ev/content.md`（3分53秒），Deep Read V6.4。

讲者延续上一节的数据中台架构，把“DataFi 内容过滤、脱敏引擎”解释为 ETL 策略层的能力，而非必须另造一套神秘系统。原始微信聊天先从 SQLite 进入 PostgreSQL 并保留，再用不同规则清洗，形成下游使用的数据集。

在清洗规则方面，讲者提到姓名、手机号、身份证号等敏感个人信息，也提到价格、辱骂、色情和其他不安全内容。这些字段要不要过滤不能一概而论，而是根据下游用途制定策略。

他用两个业务对比说明：**对外客服**不应泄露内部敏感信息，策略会相对保守；**内部销售考核或培训**可能需要特定交易价格、历史聊天上下文等，允许的数据范围不同。因此同一套原始记录可以分别经过策略 A、B、C 生成不同业务数据。

讲者认为这套规则可通过脚本或简单可视化配置实现，机器先执行数据过滤，人工复核再进行有业务含义的筛选。材料的重点是**按业务授权用途构建不同数据视图**，不是宣称对内所有数据都能无条件开放。
