# AI 编程和图像生成服务为什么都需要任务与上下文管理？

> 以“4 月 1 日企业真题解析”中的两类工程问题为例：大仓库代码修改与大量图像生成请求。

## 一、上下文窗口不是代码仓库

模型一次调用只接收有限 token。真实项目可能有几十万行代码、依赖和历史提交，把全部内容塞入上下文不现实；即使勉强放下，也会增加噪声、费用与定位难度。正确思路是让模型只读取当前任务的**必要结构与证据**。

一条有效的编程 Agent 流程是：先读项目规则和目录图→明确改动目标→检索符号、引用和测试→只展开相关实现→提出变更计划→修改最小范围→运行测试→检查 diff。发生错误时再沿调用链展开，而不是无限扩充上下文。

## 二、Rules 与 Skills 的真实作用

Rules 通常用于约束项目风格和编码纪律，例如必须通过某测试、API 返回格式、禁止触碰生产凭据。Skills 更偏向可复用的任务方法与操作指引，例如迁移数据库、审阅 PR 或处理 Office 文档。二者都可能包含 Markdown，但不能仅用“都是提示词”完全解释：它们的触发方式、调用边界和运行时工具权限可能不同，具体取决于产品实现。

把规则写下来也不能自动保证遵守，仍需可执行的格式检查、静态分析、单测与审阅门禁。

## 三、大项目“地图”和检索如何互补？

项目地图提供概念层：哪些服务负责身份、订单、支付、库存。符号搜索和语义检索提供位置层：具体代码在哪些文件。Git diff 提供变化层：本次改动实际影响哪里。三者组合才能形成“理解架构—定位实现—验证变更”的闭环。

若多个 Agent 并行改同一个工作区，容易产生文件覆盖、上下文失效与测试竞态。可以按模块分工、使用独立 worktree/分支，再通过合并和集成测试汇总结果。

## 四、10 万个图片任务不可能瞬时完成

设有效配额为每分钟 R 次，排队任务为 N 个，理想完成时间下界约为 N/R 分钟；还应扣除失败重试、耗时、供应商并发限制。比如 N=100,000，R=500，则仅按请求速率计算就至少 200 分钟，即 3 小时 20 分钟；若有效吞吐只有 300 次/分钟，则至少约 333 分钟。这些是教学计算，不是平台压测。

处理路径：API 接入验证请求、配额及去重→写入可靠任务队列→返回任务 ID→worker 按令牌桶和并发信号量取任务→调用供应商→写结果或失败状态→用户轮询或收到通知。收到 429 应依据响应头及退避策略重试；重试要设置上限、抖动和幂等键，以防重复计费。

## 五、两类场景共同的工程原则

输入量超过单次可处理资源时，不要把问题交给一个“更聪明的提示词”解决。应当定义工作单元、保留状态、选择相关上下文/请求、按容量调度，并为失败设定可追踪的恢复路径。**可控的任务生命周期**，是规模化 AI 应用与临时 Demo 的重要区别。
