# Learning｜Rerank 是 RAG 必需组件吗？应按什么条件选择？

> 原文：`output/20261025__08 为啥项目一定要Rerank_ev/content.md`。依据 Learning V0.7.0 解释原理；完整独立 Review 隔离未得到验证。

## Rerank 真正解决什么问题

初排检索会找到主题相近的候选，但它们的相关程度和是否满足限定条件不同。Rerank 在候选集合中重新比较问题与段落，把更有可能直接回答用户需求的证据放在前面。减少错误候选进入生成上下文，既可能改善答案质量，也可能降低输入 Token 开销。

不过，**Rerank 不提升第一阶段未召回的文档的召回率**：正确材料根本没进候选集合，精排就无法凭空找回它。更准确的表述应区分“召回候选覆盖率”和“重排后 Top-N 质量”，不能把二者混为一个指标。

## 为什么不是所有系统都必须加

设想知识库只有十条已按 SKU 严格过滤的 FAQ，每个问题能直接精确匹配，增加深度重排的收益可能很小，却增加额外模型调用、算力和延迟。在另一个数十万条、同义词与反例丰富的知识库里，重排价值可能显著提高。

因此可以先构造无重排基线，再比较“有 / 无 Rerank”的 NDCG、Top-N 命中率、回答忠实度和 P95 延迟。只有当收益值得支付成本时，才把它作为固定组件。

## 为什么长上下文不等于更多可靠知识

上下文越长，模型要处理的候选越多，其中可能存在重复、无关、矛盾或过期资料。选出较少且相关的片段，有时比把十几条全部送入模型更有效。但不应把“模型一定只记首尾”当作普遍规律，具体表现依模型和任务而变。

## 怎样在项目经历中说清楚

如果确实部署并测试过重排，可以描述候选数、模型、数据集、指标与取舍；如果只是方案设计，应明确写“设计/验证方案”，而不是把未实施的优化包装成已上线成果。可复现的比较比模糊的性能承诺更有解释力。
