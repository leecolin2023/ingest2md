# Learning｜多章节文旅 Agent 如何确保“没批准就不能进入下一步”？

> 源稿：output/20261025__2.25 武汉18k 教授/content.md。参考 SenseWright Learning V0.7.0；独立 Review 隔离未获验证。

## 核心问题不是有没有 interrupt，而是谁有权改变工作流状态

假设一个景区策划报告分为七章。第 1 章生成后用户可以讨论、要求修改，也可能在聊天框直接说“帮我开始第 2 章”。如果只让大模型读 Prompt 决定是否进入下一章，模型的意图理解或工具调用就可能跨越审批边界。

可以将每章的状态定义为：Draft → PendingReview → Approved 或 Rejected → Regenerating。只有后端收到**经过权限验证的批准动作**，才允许从 PendingReview 进入 Approved 并触发下一节点。普通聊天文字即使包含“我同意了”，也默认仍是讨论内容，除非业务明确将其设计为可确认且验证的正式操作。

## LangGraph interrupt 与 Checkpointer 分别负责什么

interrupt 可以让流程在指定位置暂停，并向宿主返回等待人工输入的状态。Checkpointer 可保存线程和节点状态，方便后续 resume。但二者不能替代用户身份检查、审批记录、版本号和禁止越权的后端状态机。

例如当前第 2 章已有版本 v3，审批请求至少应该绑定会话 ID、章节、版本和审批者。用户在旧窗口批准 v1，不应使已经更新的 v3 自动获批。

## 为什么修改第 1 章会影响第 3 章

若后续章节依赖前一章的预算、客流和策略结论，用户回退修改前章时，相关下游章节必须标记为需要复核或重新生成。可以维护章节依赖图，避免出现“第一章预算已经改了，后面仍使用旧预算”的情况。

## 怎么验证系统控制边界

测试应覆盖：聊天输入“进入下一章”却无审批权限、重复点击批准、旧版本审批、服务重启恢复、拒绝后重新生成、回退修改的下游失效。只有这些测试成立，才说明工作流具备可靠的人机协作控制，而不是仅在演示中弹出一个按钮。

这一场面试的重要启示是**技术组件名称与业务不变量要分别解释**：interrupt 能暂停，Checkpoint 能恢复，而审批权和状态一致性必须由完整系统规则保障。
