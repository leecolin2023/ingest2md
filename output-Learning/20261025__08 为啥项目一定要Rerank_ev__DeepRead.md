# Deep Read｜讲者为什么主张企业 RAG 一律增加 Rerank？

> 来源：`output/20261025__08 为啥项目一定要Rerank_ev/content.md`（4分02秒）。Deep Read V6.4，区分作者主张与已经证明的结论。

讲者开门见山，提出强烈主张：企业级 RAG 项目“都需要 Rerank”，甚至用“工业级 RAG 靠 Rerank 续命”来强调地位。

他解释了两条原因。其一，给生成模型过长的上下文可能稀释重点，中间材料可能被忽视；通过 Rerank 可以挑出更相关的片段，让模型聚焦。其二，向量和关键词召回对句子逻辑的理解有局限，需要更细致的相关性判断。

随后讲者列举适用情景：混合检索、多模态资料、强调回答准确性的电商客服、较大规模的企业知识库。他承认极低延迟闲聊、极简单数据、成本受限等情况下可以不加，但又从“面试包装”角度建议把项目说得足够复杂，并强调准确性优先。

课程最后讨论如何写简历：建议只表述“构建混合检索，通过 Top-K、Top-N 与 Rerank 提升召回”等相对模糊的成果，不直接写 50% 提升到 80% 的数字，因为面试官会追问指标和评测集。他把严谨统计留到后续课程，要求学员自行研究重排的原理与实现。

这段话有两条必须分开的脉络：**技术上说明为何可能需要重排**；**求职表达上鼓励强调复杂度、弱化未经检验的性能数字**。后者是讲者的面试策略，不等于实际项目已部署了相应机制。
