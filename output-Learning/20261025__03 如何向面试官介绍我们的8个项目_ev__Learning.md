# Learning｜如何把多个 AI 应用组织为有共同业务价值的系统，而非项目拼盘？

> 原稿：`output/20261025__03 如何向面试官介绍我们的8个项目_ev/content.md`。Learning V0.7.0；独立 Review 隔离未验证。

## 从业务数据流而不是技术名词开始

一家电商企业的中心对象是 SKU、客户咨询、销售流程和营销素材。若只列“客服 Agent、视频 Agent、RAG、MCP、微调”，这些技术彼此没有明确关系。

可以先画出一条链：

`销售对话 → 数据清洗和审核 → 商品知识库 → 智能客服`

再增加素材来源：

`运营生成/直播切片 → 素材管理（SKU 关联） → 客服多模态返回`

再增加共性平台：

`多业务项目 → 统一模型接入 / 权限 / 日志 / 成本 / 工具治理`

这三条关系说明哪些项目提供数据，哪些消耗数据，哪些是横向支撑层。

## 为什么“共享 SKU”很关键

同一个商品 ID 可以把聊天内容、商品权威数据、营销图片、直播片段和销售考核样本关联起来。但不能把所有数据直接放在一张向量表里：实时价格库存需要权威业务接口，宣传图片有使用授权，销售考核数据有人员权限，微调样本也有额外的训练目的和质量标准。

因此，**系统共享实体标识，不意味着共享全部数据访问权限**。

## 哪些能力应平台化

当多个项目频繁重复模型鉴权、计费、日志、API 路由、Embedding 或工具调用时，才需要抽取公共服务。平台层应明确调用契约、配额与故障责任，不因名字叫 MCP 就自动拥有所有网关能力。

## 判断项目叙述是否可信

逐项区分已上线、实验验证与未来设计。能展示系统的真实数据流、关联键、处理量、异常处理与验收结果，比把尚未实现的八个项目描述成完整生产系统更有价值。
