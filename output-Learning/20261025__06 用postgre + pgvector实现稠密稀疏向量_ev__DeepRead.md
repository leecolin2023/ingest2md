## 一、这节课先修改了一句项目描述

讲者开头检查项目材料中的“采用自定义标识符切片，解决语义截断”这一描述，认为它不准确，也限制了项目讲法，因此建议删除。

他更希望围绕真正需要解释的设计来讲：**项目采用 PostgreSQL 加 pgvector，如何在这个方案上实现混合检索？**讲者回忆，前面的项目还涉及文本、图片、视频三类数据表；同时也指出，实际项目可以选择另一种专用向量数据库，不必把一种存储方案讲成唯一答案。

## 二、他怎样区分几种检索方式

讲者先解释两类传统数据库查询：

- **精确匹配**：用户输入的词句与数据中的指定内容一致，查询才可能命中。
- **全文检索**：把查询拆成关键词，即使它们只是长文本中的一部分，也可能找到有关文档。例如文档包含“大专”“offer”，用户查这两个词，就可能定位到这条记录。

随后，讲者转向向量检索，并把混合检索理解为两种能力的组合：

- **稠密向量**侧重语义相近，即便字面不一样也有可能召回；
- **稀疏检索**侧重让有代表性的关键词起作用，强调不同词项的重要性。

他借助此前介绍过的火山引擎方案说明权重思想，并反复提到一个发音近似 `dense_weight` 的参数，用来描述语义路线与关键词路线的重要性调节。

需要保留讲者原意的一点是：这里的“稀疏”并非一套完整的技术分类定义，而是他为了面试讲解，概括为“给重要关键词更大权重”的检索直觉。

## 三、他为什么认为 PostgreSQL + pgvector 也能做类似效果

讲者认为，自己的 PostgreSQL + pgvector 方案没有直接采用视频中描述的那套“稠密／稀疏向量”的原生接口，但可以通过 PostgreSQL 的文本查询能力与 pgvector 的语义匹配能力，在 SQL 中进行组合和加权。

他声称这种模拟实现与专用方案可以做到“接近 95%”的效果；视频没有提供基准数据、指标定义或对照实验，因此应理解为**讲者的口头估计**，不能直接当成可复用的性能结论。

他想说明的关系是：不必为了“没有某个产品里的权重参数”就认为无法实现混合检索。只要分别计算语义匹配和关键词匹配的结果，并制定融合规则，就能构成一个可讨论、可调节的检索方案。

## 四、用两款护肤品解释“查询重点”与“字面命中”可能冲突

讲者举了两条商品文案：

- A：山茶花保湿精华，主打深层补水。
- B：富勒烯抗衰乳液，主打紧致、淡纹。

用户却问：“我想买那个抗老紧致的山茶花乳液。”

这里的冲突很直观：**“山茶花”是明显的字面线索，“抗老紧致”却更符合 B 的功能描述**。讲者认为，结合用户需求，应该优先理解对方要的是抗老紧致，因此倾向命中商品 B。

这个例子用来解释为什么单纯按照关键词匹配，可能和按照整体需求语义匹配产生不同排序。它也引出一个问题：两条通道的权重到底该怎么分？

## 五、在 SQL 中调权重是本节的主要工程主张

讲者给出的思路是：分别计算语义匹配得分和关键词匹配得分，再在 SQL 中设置组合权重。例如想让语义更重要，可以给语义项 0.8，关键词项 0.2；反之就调高关键词一侧。

他把这种权重配置视为对专用检索平台中融合权重参数的手动模拟，借此说明 PostgreSQL + pgvector 仍可以构造混合检索结果。

需要注意，视频并未完整展示可执行 SQL，也未给出不同分数尺度怎样归一化、不同数据库插件版本怎样兼容、以及最终如何压测的数据。因此本节传达的是**实现思路与面试论证方法**，不是经过验证的系统实现报告。

## 六、为什么最后又回到“面试不是背题”

讲者反复提醒学员：很多面试不会完全照着课程原话问，所以不能只记住一个方案或某个参数名。应该能解释传统精确查询、全文检索、稠密向量、关键词权重之间的关系；当别人问到另外一种架构时，也能讨论它是否可以实现、怎样实现以及有什么不同。
