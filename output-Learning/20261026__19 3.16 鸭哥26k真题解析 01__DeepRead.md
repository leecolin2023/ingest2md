# 鸭哥 26K 面试真题（上）：业务、RAG 实时性与高并发

## 面试回放先分辨哪些问题有价值

直播开头讨论某 AI 赋能岗的薪资与方向，随后展示“鸭哥”的面试问题。讲师将基础技术问答、业务理解、模型微调、跨境电商流程、企业 AI 价值等题目逐一归类。他认为技术名词的定义相对容易准备，真正困难的是高并发、知识库数据变化和跨服务的状态管理。

讲师提供一条业务回答框架：从产品创意、流量获客、销售转化三个环节说明 AI 如何参与企业经营。服装设计、主图与商品文案、智能客服是对应例子。他把这一方法称作对企业不同价值环节的理解，而不是只讲模型 API。

## RAG 商品信息频繁变化：把动态字段分离出来

20 分钟左右开始进入本次较完整的技术案例。问题是：商品频繁上架、下架、改价时，如何让知识库近实时更新且不必每次重新 embedding？

讲师先构造“库里篮球鞋”的示例。品牌、材质和商品介绍等相对稳定字段存入知识库；价格、库存、销售状态等高频变化字段放在 Redis，并由商品 ID 建立关联。检索先找相似商品，再凭 ID 取动态字段，于是价格更新不要求重建商品介绍的向量索引。这是他所谓的“动静分离”。

随后扩展到 **CDC**：源业务数据库有变化，捕获变更日志，异步更新 Redis 或其他查询侧数据；再通过版本号、时间戳、软删除或状态过滤避免返回已下架商品。讲师举例先向量召回较大候选集，再关联动态字段过滤无效数据，最后留下可答复的商品。他强调这些方法可以组合使用。

## 高并发不只靠一台更强的服务器

后段问题转到流量洪峰。讲师先提云原生弹性扩容，再给没有自动扩容时的分层思路：入口网关限流，消息队列削峰，Redis 分担重复查询，服务超时做降级或备用模型，CDC 更新在高峰期合并写入。他用“餐馆只能同时容纳有限顾客，后续排队”解释消息队列。

## 原文的重点与局限

重点不是给出一套可直接部署的代码，而是训练求职者：先区分常变与不常变的数据，再区分读请求、写入更新和突发流量，各自在相应层次解决问题。材料里若干 Redis 持久化与 CDC 延迟的讲法是口语化示意，没有给出可靠的故障恢复或一致性证明。
