# Learning｜一个能回答商品问题、还能返回图片和视频的 RAG 客服，数据应该怎样设计？

> 学习对象：`output/20261025__04 客户系统的Rag到底怎么建？_ev/content.md`（10 分 37 秒）  
> 使用 SenseWright System Learning V0.7.0 的知识主干组织方法。Deep Read 对应同名稿；本轮未获得独立 Review 模型调用记录，不将其表述为已通过完整 D/R 隔离验收。

## 1. 先弄清楚：客服回答的“知识”究竟来自哪里？

假设电商企业有十个左右的 SKU。客户在聊天里问“这款耳机适合运动吗”“有哪些颜色”“多少钱”。销售此前回答过大量相似问题，商品库里有规格、库存和价格，素材库里有图片、演示视频。

这些内容不能不加区别地当作同一种文本处理。因为它们回答的问题不同：

- **商品主数据**负责确认“这到底是哪款 SKU”，并提供价格、库存、规格等需要保持权威和更新的数据。
- **聊天记录和商品介绍**包含更口语化的问法、卖点、使用场景和解释，可以作为 RAG 的知识片段。
- **图片与视频素材**提供可展示的媒体对象，本身需要与商品建立明确关系。

所以，RAG 的第一步不是选择 Embedding 模型，而是确认系统中有哪些业务事实、哪些知识文本，以及它们分别归谁维护。

## 2. 清洗之后，为什么还要绑定商品 ID？

举例：原始聊天记录说“这个充电很快，出差用特别方便”。孤立地做向量化，系统或许能找到“快充”相关内容，却不知道“这个”指的是哪个商品。

人工清洗时，除了去噪和纠错，还要为记录补上商品 ID、适用 SKU、业务场景和审核状态。这样，查询“某款耳机的快充能力”后，系统才能只用关联该商品的证据。**Embedding 解决语义近似的问题，商品 ID 解决业务实体归属的问题。**两者无法互相替代。

一份简化的逻辑数据模型可以是：

`products(product_id, sku, name, price, stock, updated_at)`  
`knowledge_chunks(chunk_id, product_id, content, embedding, source_id, version)`  
`media_assets(asset_id, product_id, media_type, url, description, embedding)`

这些只是为了说明关联关系的示例表名，并不是视频作者已经建成的数据库表。实际设计还需要权限、删除与更新同步、审核状态等字段。

## 3. PostgreSQL 和 pgvector 的分工

PostgreSQL 是关系数据库，擅长保存商品主数据、进行条件过滤、建立外键关联和执行事务。pgvector 是扩展，它让 PostgreSQL 能保存 Embedding，并按向量相似度检索候选记录。

因此，一条数据可以同时有 **结构化字段** 和 **语义向量**：先按商品、租户、有效状态等条件缩小范围，再在允许的知识片段里做向量检索。pgvector 官方也说明可以结合 PostgreSQL 全文检索组成混合检索，再通过 RRF 或交叉编码器融合结果。

这里要区分两个容易混淆的概念：

- **检索相似的解释**：“这款耳机适合健身吗？”可以从产品介绍和历史问答中找证据，再由模型综合回答。
- **读取权威业务值**：“现在多少钱、还剩多少库存？”应查询商品主数据或业务接口，不能把向量检索到的一段历史销售话术当成当前价格。

相关技术依据：[pgvector 官方文档](https://github.com/pgvector/pgvector)、[PostgreSQL 全文检索文档](https://www.postgresql.org/docs/current/textsearch-controls.html)。

## 4. 图片和视频为什么不能仅凭“像不像”找到？

假设客户问：“给我看看这款耳机佩戴效果的视频。”

一种易错实现是：拿客户问题向量化，在所有视频描述中搜索相似内容，然后返回排第一的视频。问题是，第一名可能展示的是另一个型号，甚至是竞争商品。

更可靠的方式是：先识别并确认客户要的是哪个商品或 SKU，在对应商品权限范围内检索视频描述；拿到媒体记录后，返回经过校验的 URL。此时，**商品 ID 保证不串商品，语义检索负责找到对的问题素材**。

对于需要展示图片和视频的客服，还要明确前端返回协议：文本答复、商品卡片、图片列表和视频链接可以同时出现，但数据字段必须可追溯，不能由大模型随意捏造图片地址。

## 5. 一次“这款耳机多少钱”的请求该怎么运行？

可以按下面这条实际执行链理解：

1. **理解请求**：识别问题是询价，同时从上下文确认“这款耳机”对应哪个商品。如果无法消歧，应继续询问型号。
2. **查权威数据**：通过商品 ID 或 SKU 查询商品表、价格服务，获得当前有效价格、币种、促销条件和更新时间。
3. **按需补充知识**：如果用户还问“为什么贵”，再检索该商品的卖点、规格说明及售后政策。
4. **组织答案**：将已取得的结构化值和知识片段交给生成模型。价格数字来自业务记录，不由模型估算。
5. **返回可溯源结果**：输出商品名称、价格和必要说明；需要时附相关媒体链接或商品卡片。

这条链路是对视频中未讲完的最后一个问题所作的教学扩展，并非视频原话。

## 6. 怎样判断数据库结构设计得对不对？

不必一开始搭建大规模知识库。先挑一组真实提问，覆盖“精确型号”“代词指代”“历史话术与现价冲突”“文本转图片/视频”“不同 SKU 的同名商品”等情况。

查看每次请求是否满足三个条件：**查对商品、拿对事实、返回对媒体**。如果商品 ID 正确但价格过时，应检查权威数据与缓存更新；如果商品 ID 错误，应检查实体识别、上下文关联或数据标签；如果商品 ID 正确却选错知识段落，应分析切片、检索与重排。

这个区分能把“模型答错了”还原成可定位的系统问题，也是这节视频真正值得吸收的工程思路。
