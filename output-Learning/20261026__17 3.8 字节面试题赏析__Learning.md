# AI 应用性能优化中的三种机制：前缀缓存、语义缓存与模型路由

> 基于“字节面试题赏析”原稿展开机制学习；教学示例不代表特定云服务的实测结果。

## 一、为什么需要先区分缓存层级？

一次 RAG 请求常经过：业务提问→文档检索→组装提示词→模型预填充→生成答案。不同缓存消除的是不同成本。

**KV Cache** 保存 Transformer 注意力计算中已处理 token 对应的 Key/Value，主要避免同一序列生成时反复处理历史内容。**Prefix Cache** 在服务引擎允许的范围内复用相同 token 前缀的计算结果，可能跨轮次或跨请求共享。它要求实际 token 序列满足对应的复用条件，而不是只要求“语义相似”。**业务响应缓存** 在 Redis 或其他存储中保存输入与最终输出，命中时可能完全不再调用模型。

三者分别节约计算中间结果、重复预填充、整个生成请求，收益指标和失效条件不同。

## 二、RAG 动态检索怎样影响前缀？

假定提示词由系统规则 S、稳定常识 F、动态检索结果 D、用户问题 Q 构成：

`S + F + D + Q`

若 S 和 F 的 token 序列稳定，即使 D 每次变化，共同前缀仍可能命中。若 D 排在最前面，则变化会更早打断公共前缀。固定排序只有在同一组检索片段确实相同时才帮助复用；若任意把低相关片段置前，可能牺牲检索质量。正确做法是测量前缀命中率、TTFT、Token 成本与答案质量，而不是只为缓存改变语义排序。

## 三、为什么“问法相近”不足以共享答案？

响应缓存的 key 可以是精确文本，也可以是 embedding 相似结果。但语义接近不等于业务动作相同：“办理贷款”与“查询贷款”涉及不同授权、流程和状态。一个更稳健的流程是：候选问题召回→核对意图、参数、租户与知识版本→满足条件才返回缓存答案→否则走实时业务系统或模型。高风险领域还需检查数据过期、个人信息隔离以及是否存在即时性字段。

讲师提出的小模型二次判定可作为实现选项，但不是通用强制步骤；如果校验代价接近直接调用模型，缓存的经济收益就可能消失。

## 四、模型路由为何不能只写一个 if/else？

按用户会员等级切换模型是**静态业务规则**；按输入语言、长度、工具需求、复杂程度以及容量状态选择实例，才涉及更丰富的动态路由。路由器还要定义失败反馈：超时是否重试、是否降级、降级后准确率损失能否接受、哪些请求不可降级。

离线评测集用于比较不同路由与答案策略；在线日志、Trace、异常率、投诉与采样标注负责发现线上异常；发现 bad case 后再加入回归评测。评测集本身不会自动“监控”系统，必须接入真实运行链路。

## 五、复述一条完整的工程链

用户发问→业务身份与权限校验→知识检索与版本绑定→检查响应缓存→选择模型/实例→构建稳定前缀提示词→生成→记录耗时、缓存命中及质量反馈。这条链把缓存、RAG、路由、监控放在同一个系统内，能够解释它们为什么互补、分别会在哪里失效。
