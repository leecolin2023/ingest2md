# 多 Agent 系统什么时候需要共享状态？客服转人工又该怎样排队？

> 依据“鸭哥 26K 真题解析下篇”展开。原稿包含两个相关的系统设计问题：资源有限时的排队，以及多个执行者共同处理一个任务时的协调。

## 一、客服排队本质上是有限服务能力分配

如果客服有 C 个席位，短时间到达的用户数远大于 C，系统就需要维护排队状态。FIFO 最容易理解，但当部分事项具有更高时效性时，可以设置业务优先级。任何优先队列都可能产生**饥饿**：低优先级用户始终得不到服务。因此可以让优先级随等待时间提高（aging），同时规定最大等待、投诉升级和公平性边界。

一条完整的转人工链路是：AI 识别转接意图→收集必要信息→创建排队任务与会话 ID→安排席位→推送等待状态→席位接入后交付上下文摘要→人工完成服务→记录结果与反馈。预计等待时间应根据实际到达率、处理时长和可用席位估算，而非写死。

“隐藏入口”虽然能保护系统，但可能伤害客户权益；紧急、安全或监管相关事项不能简单按商业价值排后。超载时可提供回呼、留言、明确 SLA，而非无提示丢弃。

## 二、多个 Agent 并不天然意味着并发共享状态

**串行编排**：A 的结果给 B，B 给 C。优点是步骤和状态归属清晰；代价是延迟叠加。

**并行分支**：A、B 同时独立检索不同来源，再由聚合节点 C 汇总。只有分支真正无共享写入冲突时并行才简单。

**跨服务协作**：任务在不同机器间恢复执行，必须有统一身份、状态持久化、重试及错误处理，与串行/并行是两个维度。即使任务串行，跨机器仍可能需要持久化和调度。

## 三、分布式状态由四项机制组成

1. **身份**：每项任务有全局 task/thread ID，不能把不同用户会话拼在一起。
2. **持久化**：checkpoint 记录已完成节点、输出与后续待运行节点；选择事务性数据库或可靠状态存储。
3. **执行控制**：工作队列、租约、超时与重试决定哪个 worker 可继续执行，并处理重复消息。
4. **一致性与恢复**：版本号、乐观并发控制或锁防止冲突写入；补偿操作与幂等性处理外部工具调用。

Redis 锁不负责业务拓扑，消息队列不保证业务动作恰好执行一次，数据库 checkpoint 也不自动解决跨服务调度。必须将这几项共同设计。

## 四、先判断是否值得并行

当任务可以独立分解、耗时长、聚合规则清晰，并行有价值；当任务高度依赖上一步输出、状态共享密集或错误恢复复杂时，串行更可靠。设计判断应比较总延迟、成本、重复执行风险及维护复杂度，而不是把“并行 Agent”作为默认的成熟标志。
