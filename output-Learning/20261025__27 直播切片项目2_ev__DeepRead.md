# Deep Read｜直播切片项目的并发瓶颈在哪里

> 原稿：`output/20261025__27 直播切片项目2_ev/content.md`（5分20秒）。Deep Read V6.4。

讲者以“视频切片项目遇到高并发怎么办”为面试题，先复盘其架构选择：把原来在服务端运行的部分 FFmpeg 处理任务移到浏览器或客户端，从而减少服务器算力负担。

他认为剩余的主要重量级任务在 ASR 语音识别服务，因此云端 ASR 的配额和处理容量比“创建任务的 HTTP 接口”更值得关注。讲者提出通过购买云服务额度，或准备多个 ASR 提供商作为备份方案。

接着他谈任务调度和进度展示：用户点击开始后，服务端记录异步处理任务，前端订阅进度。即使同时新建一百个任务，创建任务本身的请求量也很有限，因此他认为此处没必要仅仅为了创建任务而引入消息队列。

这段论证的关键是**创建任务的 QPS 不等于后台任务处理吞吐**。但讲者倾向认为“把重活交给 ASR 云厂商，就不存在扛不住问题”，属于较强的口头判断。视频没有证明服务商容量、成本和并发配额一定满足需求，也没有完整讨论浏览器端资源、失败恢复与排队机制。

全文强调根据实际压力位置选择优化点，而非为了技术栈丰富就添加消息队列。
