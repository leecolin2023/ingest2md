## 1. 先把三个概念分开

**精确查询**一般是对确定字段或字符串执行明确匹配，例如用 SKU 查商品。它要求满足给定条件，适合型号、唯一标识和权威业务记录。

**全文检索**先对文本进行解析、分词、建立索引，再计算词项相关性。例如查“抗老 紧致”，即使这两个词分散在商品介绍中，也可以把相关记录找出来。PostgreSQL 内置 `tsvector`、`tsquery`、`ts_rank`、`ts_rank_cd` 等机制，支持这种词法检索。

**向量检索**先使用 Embedding 模型把文本映射到数值向量，比较查询向量与文档向量之间的距离或相似度。它更适合处理同义表达与语义泛化，但并不天然保证精确商品型号正确。

这三种方法解决的是不同问题，并不是“越新就全面替代越旧”。

## 2. 稠密向量、稀疏向量和 BM25 是同一回事吗？

不是。

稠密向量（dense vector）通常有大量连续维度，每个维度都携带浮点值，适合表示文本的整体语义。稀疏向量（sparse vector）则只有少量维度非零，常见用途是表达词项或特征的重要性。

BM25 是经典词法检索的相关性排序方法，不要求神经网络输出稀疏向量。由神经网络生成的稀疏表示、BM25 词项得分和 PostgreSQL 的全文检索排名，也不是同一个算法。

pgvector 不仅支持常见的 `vector`，还提供 `sparsevec` 类型；不过，**能存储稀疏向量**并不等于**自动具备某种学习型稀疏检索模型**。如果只是把 PostgreSQL 全文检索与 pgvector 组合，应准确称为“词法 + 语义”的混合检索，而不是声称已经原生实现某种专用神经稀疏向量服务。

依据：[pgvector 官方 README：Sparse Vectors 与 Hybrid Search](https://github.com/pgvector/pgvector)、[PostgreSQL 全文检索排序](https://www.postgresql.org/docs/current/textsearch-controls.html)。

## 3. 为什么用一个 PostgreSQL 就可以做两条检索通道？

假设有一个商品知识片段表：

`chunks(id, product_id, content, embedding, textsearch)`

其中 `embedding` 保存文本向量，`textsearch` 保存 PostgreSQL 可用于全文检索的词项表示。一次查询产生两路结果：

- **语义通道**：把用户问题转成 Embedding，按 `embedding` 的向量距离由近到远排序。
- **词法通道**：把用户问题转成 `tsquery`，按全文索引匹配，再用 `ts_rank_cd` 等函数排序。

两路各取一批候选，把相同 `id` 合并去重，再做融合排名或使用 Reranker 精排。

注意 PostgreSQL 自带的 `ts_rank` **并不是 BM25**，所以不能简单把 `ts_rank` 的得分叫 BM25 分数。中文文本还要额外关注分词词典与索引策略是否适合中文。

## 4. 两种不同的打分为什么不能直接相加？

向量相似度与全文检索分数来自不同计算机制，尺度往往不一样。直接计算

`0.8 × 向量相似度 + 0.2 × 全文得分`

只有在两个分数的方向、范围和含义都经过处理时才有可解释性。否则，系数虽然写成 0.8 和 0.2，实际结果可能几乎完全由数值范围较大的通道控制。

有两条容易上手的方案：

**方案 A：先做分数归一化，再加权。**在同一查询的候选集中把两路得分映射到可比范围，再根据业务与评测集选择权重。要谨慎处理异常值，以及不同 Query 分数分布的差异。

**方案 B：用 RRF 倒数排名融合。**只利用各通道的名次，计算

`RRF(d) = Σ 1 / (k + rank_i(d))`

其中 `k` 是平滑参数，文档如果在两路排名都靠前，融合得分就更高。RRF 避开了不同分数尺度直接比较的问题，pgvector 官方也将其列为混合检索的融合选项。

两条方案均可以再接 Reranker。RRF 负责融合候选，Reranker 则进一步判断 Query 与候选之间的相关性。

## 5. 用“抗老紧致的山茶花乳液”理解检索意图

课程中的两条商品记录是：

- 商品 A：“山茶花保湿精华，主打深层补水。”
- 商品 B：“富勒烯抗衰乳液，主打紧致淡纹。”

客户问：“我想买那个抗老紧致的山茶花乳液。”

词法检索可能因为“山茶花”命中 A，向量检索可能因为“抗老紧致”更接近 B。讲者希望借此证明，语义与关键词在实际问题里有不同作用。

但在真实客服系统里，这句话还暴露了一个**业务实体冲突**：“山茶花乳液”像是在指认特定商品，“抗老紧致”像是在描述期望功效。若系统直接提高语义权重，把 B 当成唯一确定答案，仍可能买错产品。

因此，需要区分两种意图：

- 用户明确在找某个指定商品：应先核对商品名称、SKU、品牌等硬条件。
- 用户更重视功效、接受替代推荐：可以让语义匹配发挥更大作用，并解释 B 为什么更符合目标。

无法区分时，可以向用户确认：“你要找山茶花系列，还是想找主打抗老紧致的产品？”这比单纯调大某一路权重更可靠。

## 6. 如何判定权重和架构是否适合业务？

先准备少量带正确答案的业务问题，覆盖精确型号、自然语言改写、同义词、实体冲突、历史数据与现价冲突等类别。用同一批查询分别测试词法检索、向量检索和融合检索。

看三层结果：**相关证据是否被召回（Recall@K）**、**正确候选是否排在前列（例如 MRR 或 nDCG）**、**最终回答是否用对业务实体和事实**。再看 P95 延迟以及资源成本，确定是否值得增加重排。

视频中“接近 95% 的效果”没有说明指标和测试方法，不能当作 PostgreSQL + pgvector 对另一种平台的固定性能比例。工程上真正需要证明的是：在你的数据上，采用哪种组合能以可接受成本产生更好的真实检索结果。

**最后形成一个判断：** PostgreSQL + pgvector 适合在同一业务数据库里联合结构化过滤、全文检索与向量检索；是否要换专用检索产品，不取决于它名字里有没有“稠密、稀疏”，而取决于现有方案能否满足准确性、延迟、规模、隔离与运维要求。
