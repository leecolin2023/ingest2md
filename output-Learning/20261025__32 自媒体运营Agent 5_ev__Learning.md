# Learning｜Agent 调用外部 API 不稳定时，限流、重试、熔断、降级应该怎么配合？

> 来源：`output/20261025__32 自媒体运营Agent 5_ev/content.md`。依据 Learning V0.7.0，完整独立 Review 模型隔离未验证。

## 四种手段分别管什么

**限流（Rate Limiting）**阻止单位时间进入系统的请求超过预算。例如图片生成每分钟最多接收一定次数，用于控制成本与保护容量。

**重试（Retry）**应对短暂的网络异常、可重试超时或部分限流响应。指数退避使连续重试间隔逐渐增长（例如 1、2、4 秒），再加随机抖动（Jitter）可避免大量客户端同一时刻重试造成更大拥堵。重试必须有次数、总时限以及幂等性约束。

**熔断（Circuit Breaker）**用于发现依赖持续失败时主动拒绝新请求。Closed 正常运行，Open 快速失败，Half-open 放行少量试探请求。它防止大量请求和重试不断压向故障依赖。

**降级（Fallback/Degradation）**是在核心能力暂不可用时提供可接受的替代路径，如图片生成暂时返回已有素材、RAG 向量检索退到词法检索、主模型切换到已授权的备用模型。

## 为什么不能机械按“先限流后重试再熔断”理解

请求经过不同组件时，它们可能同时发挥作用。限流通常在接入层判断，熔断器可能在调用外部依赖之前判断；可重试错误触发退避，持续失败则可能打开熔断器；降级可以发生在明确的错误或断路状态。

保护措施的配置关键是**错误分类和总时间预算**。如果图片生成 API 处理了请求但响应超时，盲目再次提交可能被重复收费或产生重复图片，应使用任务 ID 或幂等键核查。对用户无感、昂贵且长时延的图片生成任务，异步排队可能比同步多次重试更适合。

## 对不同节点采取不同措施

- 意图识别：短超时、错误兜底、必要时澄清用户；不能认为云厂商服务“绝不会挂”。
- RAG 查询：故障时尝试权限安全的词法检索，必要时明确告知知识检索不可用。
- 图片生成：按用户、租户、计费额度限流，使用队列，设置重试上限，主服务持续故障时切换有质量标准的备用路径。
- 外部下单和付款：避免自动重试导致重复交易，优先幂等性验证。

## 怎样检验整个方案

构造故障注入：让一个上游接口超时、持续返回错误、恢复正常，观察是否出现重试风暴、排队失控、重复收费或错误降级。记录成功率、P95 延迟、失败隔离时间、成本与用户可接受的结果。目标不是让链路永远“成功返回 200”，而是在有限成本和明确业务边界内安全退化。
