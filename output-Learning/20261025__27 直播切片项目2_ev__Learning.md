# Learning｜视频切片系统怎样做容量规划？为什么创建任务少不等于没有并发问题？

> 来源：`output/20261025__27 直播切片项目2_ev/content.md`，Learning V0.7.0；独立 Review 模型隔离尚未验证。

一个视频处理系统至少有三类工作：**接收请求并建任务、执行媒体处理与 ASR、通知用户进度与结果**。它们的吞吐单位不同。

假设一分钟内 100 个用户各创建一个任务，接口 QPS 只约 1.67；但若每个视频需十分钟 ASR，后台就可能累积一千分钟的处理量。即使接单接口毫不费力，处理服务仍会出现等待队列。不能由低 QPS 推出没有并发瓶颈。

## 为什么把 FFmpeg 移到浏览器可能有效

本地分离音轨、简单剪裁或预处理能够减少服务端 CPU 与网络传输，但前提是浏览器设备性能足够、格式支持可靠、用户隐私合规且不会因中途关闭页面造成任务丢失。它是**计算责任迁移**，不是凭空消除了成本。

## ASR 云服务如何约束吞吐

需要核实每个供应商的并发任务数、每分钟音频额度、文件大小、时长限制、失败重试和价格。多个供应商只有在接入、模型质量、数据合规与故障切换均得到验证时才是可靠备份，不等于随意切换即可无限扩容。

## 什么时候需要队列

即使任务提交 QPS 不高，长耗时异步处理仍可能需要持久任务队列来限并发、处理失败、恢复进度和调度优先级。可以先用数据库任务表和受控 Worker，规模增加后再考虑专用消息队列。选择依据是**后台积压、恢复需求和并发控制**，而不是简单看 HTTP 请求是否达到每秒上百次。
