# Learning｜为什么 RAG 已经有向量相似度，还可能需要 Rerank？

> 来源：`output/20261025__07 Topk N Rerank_ev/content.md`；Learning V0.7.0 知识结构，独立 Review 模型隔离尚未验证。

## 两阶段检索的机制

当知识库很大时，直接把每个查询与每条文档一起送入深度模型评判，成本会很高。工程上常采用两阶段：先由 BM25 或向量索引**快速召回 K 个候选**，再用较昂贵的相关性模型重排，最后选 **N 个上下文片段**。N 通常小于或等于 K。

粗召回强调不漏掉有可能正确的证据，精排强调把真正符合问题条件的资料排在前面。这是两个不同的优化对象。

## 为什么向量相似有时会误判

例子：客户问“适合跑步且不掉落的耳机”，候选 A 是“跑步时稳定佩戴”，B 是“请勿跑步佩戴，容易掉落”。A 和 B 在主题词上都很接近，向量模型未必充分区分否定含义。交叉编码器类型的 Reranker 将 `Query` 与每条 `Document` 共同输入模型，交互建模后得到相关性判断，通常更容易利用“请勿”等局部逻辑线索。

这不意味着 Reranker 保证不出错：输入证据本身错误、模型不擅长领域词、上下文被截断，都可能影响判断。

## Top-K 和 Top-N 怎么设置

课堂中的 K=15、N=3 是教学示例，而非统一参数。K 太小，可能在第一阶段就漏掉正确段落，此时精排无从补救；K 太大，会显著增加重排成本与延迟。N 太小可能使生成缺少完整依据，N 太大则增加上下文开销和噪声。

可以用标注了相关文档 ID 的测试集比较候选 Recall@K，再在相同输入下检查排序指标（MRR、nDCG）、最终回答质量与 P95 延迟。选择能满足业务精度和服务成本的组合。

## 检索与生成的边界

Rerank 决定的是**哪些候选更值得给生成模型看**，不会自己生成业务答案。生成模型仍需根据排序后的可信资料组织内容、处理多片段冲突，并在证据不足时说明不确定。
