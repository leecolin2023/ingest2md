# 从 AI 求职热度到真实能力：用 SFT 与 DPO 案例理解什么叫掌握项目

> 根据“二期新同学与面试题解读”直播，聚焦可复述的工程机制，不把培训机构的行业预测当成事实。

## 一、岗位需求和培训热度不是同一指标

AI 岗位可能来自原互联网企业的新工具链，也可能来自传统企业的流程自动化需求，但二者对工程师的要求不同。前者通常关心可维护代码、服务稳定性与系统集成；后者可能更关心业务流程、数据权限、投入产出比。培训咨询人数增加只能说明关注度，不能直接证明岗位净增长、薪资涨幅或录用率。

求职者可以用招聘启事中的任务频率、真实技术要求、城市、薪资和年限判断需求，而不是仅靠课程报名热度。

## 二、以“销售客服语气微调”理解一个完整项目

**目标**：让模型的语言风格更接近企业的合规客服话术，而不是让模型“知道更多产品事实”。产品价格、合同条款等更新快的知识更适合由检索或业务 API 提供。

**数据**：从获得授权的客服对话中去标识化，按对话轮次拆分样本，清理广告、表情、无效回复与敏感信息。按会话或客户分离训练与验证集，避免同一对话同时出现在两边引发虚高指标。

**SFT（监督微调）**：构造输入上下文和期望答案对，让模型学习如何响应客服任务。可理解为“给出合适行为的示例”。

**DPO（直接偏好优化）**：对同一提示准备偏好答案与不偏好答案，让训练目标倾向更符合业务要求的输出。它不是简单的“道德训练”，而是针对偏好对进行优化；样本质量决定学到的偏好。

**评估与上线**：至少比较基座模型与微调模型在业务正确性、语言一致性、拒答与隐私方面的差异。灰度放量必须观察真实指标和风险，才能逐渐扩大。

## 三、为什么“数据—训练—评测—上线”比背参数更关键？

学习率、epoch、LoRA rank 等参数有重要作用，但单独记住参数名无法说明训练解决了什么。工程上先定位失败类型：数据标注错？格式不对？过拟合？基础知识缺失？推理模板或采样参数变化？确定原因之后才决定加数据、改训练或改检索。把结果不佳都归因于“参数没调好”，会浪费算力。

## 四、怎么检验自己真的理解了这个项目？

能够说明一条原始对话如何变成训练样本，SFT 与 DPO 分别改变什么，怎样避免隐私外泄、怎样比较上线前后的收益，并能提供实验记录。这比只会把课程描述移植到某个公司背景更能证明工程能力。简历中只能声明自己真正做过并能提供证据的环节。
