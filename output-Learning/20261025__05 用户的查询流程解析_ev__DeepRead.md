# Deep Read｜电商客服的查询链怎样从意图走到答案

> 来源：`output/20261025__05 用户的查询流程解析_ev/content.md`（3分39秒）。遵循 Deep Read V6.4，恢复原文结构，不把设计示意冒充真实实施。

## 从“耳机多少钱”到两个意图判断

讲者以用户问耳机价格或其他商品问题为入口，首先强调：不能收到一句话就直接检索整库。系统应先做意图识别，可由一个轻量大模型完成。它的任务有两个：**判断用户说的是哪个 SKU**，以及**判断应该返回文字、图片、视频还是其他形式**。

SKU 并非固定写在提示词里。讲者建议由后端接口动态提供当前商品列表，例如原来十个 SKU，新增后变成十一个，意图识别也应跟着使用最新名单。

## 为什么需要对话上下文

用户可能经历五轮、八轮甚至十轮交互，先询价、再问外观、最后索取下单链接。同一句“那这个呢”如果脱离前文，系统很难判断商品归属及下一步应该返回什么。讲者因此提出每轮意图识别需要参考完整对话，并强调用户意图会随交互推进而变化。这是他为系统连续性提出的设计思路。

## 检索不是直接扫整库

识别 SKU 后，讲者假设系统使用 PostgreSQL + pgvector，先通过关系字段做**精确过滤**，只留下当前 SKU 对应的数据，再在这个子集里做向量检索。例如知识库有 1000 条、10 个 SKU，平均每款约 100 条，则可以先从 1000 缩到约 100，再检索文本知识。最后由大模型组织回答。

材料把文字、图片、视频都放在同一个商品关联框架下，但本节主要演示文字检索，没有进一步讲图片和视频完整返回接口。

## 作者的认知主线

**识别业务对象 SKU → 识别回答形式 → 利用多轮上下文消歧 → 按 SKU 过滤知识记录 → 向量检索 → 大模型生成回答。** 讲者把这一过程作为面试时应能够举一反三、而不是死背技术名词的示范。
