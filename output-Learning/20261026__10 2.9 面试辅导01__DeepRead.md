# Deep Read｜语音客服项目面试辅导：从项目背景到性能、监控和部署

> 原稿：output/20261026__10 2.9 面试辅导01/content.md（约36分41秒）。SenseWright Deep Read V6.4，完整覆盖型。本文还原讲者的建议，不把虚构项目和参数转为已验证事实。

## 项目叙事和工作边界

讲者先以智能客服、实时语音与自媒体运营是多个行业都可能需要的服务为起点，建议学员结合电商或教育业务讲述项目。课程反复鼓励根据需要编造公司、团队人数、个人职责与保密理由，甚至在无法展示系统时借“在职偷偷面试、签了保密协议”回避证据。这是讲者的**面试包装策略**，不是对真实实施的描述。

## 性能优化的分层讲法

讲者希望候选人不要只回答“调用了大模型”，而应从整条链路分层展开。模型侧涉及不同豆包模型版本的取舍、提示词前缀缓存、稳定内容放前动态内容放后、输出 Token 上限、Temperature 和流式输出。他甚至建议以“开启深度思考获取更高优先级计算资源”解释速度改善，但原文没有服务商证据或对照测试。

RAG 侧强调混合检索、数据标签过滤和重排：例如教育公司按初中、高中等课程标记，或电商根据 SKU 过滤，之后调节语义与词法匹配权重，缩小给模型的 Top-N。讲者将这些选型作为一组可说的优化亮点，而不是报告通过评测获得的提升值。

语音侧涉及 ASR 双向流、音频分包尺寸、热词、情绪识别、TTS 流式合成与语速、RTC 的 SFU 转发、UDP、前向纠错 FEC、网络抖动与打断。他明确指出“情绪检测”尚未实现，却仍建议面试时宣称已使用，必须保留这一事实边界。

## 可靠性和观测

讲者从 RAG 故障与 LLM 降级谈到备用模型、兜底话术、日志。建议每次请求生成统一 ID，关联 Prompt、RAG 命中、模型响应和 Token 用量，并用 ELK 等界面检查。Prometheus/Grafana 他承认当时未接入，计划日后演示。这与已真正完成的项目监控不能混为一谈。

## 评测、部署和后续迭代

课程介绍构建固定问题集、记录黄金答案、夜间运行评分，用其观察模型和 RAG 变更影响；又描述 Python 服务、PostgreSQL、Docker Compose、反向代理和 CI/CD 的部署思路。对长期记忆、数字人等补充功能，讲者说部分仍在开发、未提交或选择不做。

综上，这场辅导的真实认知结构是**跨行业项目叙述 → 模型/RAG/语音三层优化 → 日志与评测 → 部署 → 扩展**。其中很多配置是教学设想或鼓励虚构的面试话术，不能视作课程已提供了生产压测与项目验收记录。
