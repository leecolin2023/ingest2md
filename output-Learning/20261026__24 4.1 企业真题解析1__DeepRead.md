## 主题一：Cursor Rules、Skills 和 AI 编程规范

讲师先讨论把项目开发规范写入 Markdown，让 AI 在编程时遵循。所举示例涉及后端项目的 Python/FastAPI 约定、前端 React/Tailwind 风格、Git Flow 与提交规范。他把 Rules 看成按文件或项目范围生效的约束，把 Skills 类比成包装好的提示词与最佳实践，重点强调用户不必每次从零长篇描述自己的编码习惯。

他建议在项目中明确指出需要哪些规范与上下文，而不是让模型每次重新检索整个 Skill 库。这部分重点是“上下文应该精确传给编程 Agent”，并非对各产品当前 Skills 执行语义的严格规范说明。

## 主题二：几十万行代码为什么不能一次装进上下文

讲师用一个假设的 30 万行代码项目说明上下文窗口的限制，给出三个互补方向：

1. **精准喂料**：指定目标文件、目录、方法；过滤 node_modules、生成文件等无关内容；把模糊的“帮我重构目录”改成明确目标和限定文件。
2. **分层描述**：维护项目地图 Markdown，解释技术栈、关键模块、接口、数据流；各模块 README 保存业务职责、外部接口与依赖。复杂问题采用从宏观到局部、逐层缩小范围的“洋葱式”探索。
3. **工程增强**：使用代码索引或语义检索定位相关片段；把不同任务交给独立上下文，但尽量避免多个实例同时修改同一文件；利用持久化笔记保留阶段结论；代码审阅优先看 Git diff/PR 而不是无差别读完整仓库。

讲师坦言，部分功能他自己没有实际用过，是对工具文档或模型整理方案的讲解。

## 主题三：10 万个图像生成任务如何处理

后段从企业面试题切到 AI 文生图服务。讲师先指出第三方图像模型有速率和并发上限，不能把用户需求量直接等同于可瞬时处理量。方案分成接入层、任务队列和 API 调度层：入口校验参数、限流、查缓存、生成任务 ID；队列保存待处理任务；调度器按供应商并发与每分钟额度放行，接到 429 时指数退避重试，超过阈值后失败或降级。

材料把消息队列类比成餐厅排队系统；具体“每分钟 500 次”是示意，不等于某平台的正式配额。

## 贯穿的同一个思维

无论是庞大代码库还是高并发图生图，讲师都在讨论**资源有边界时如何安排工作**：前者是上下文窗口与模型注意力有限，后者是外部 API 调用额度有限。把工作变成有范围、有优先级、可恢复的任务，比“直接把所有输入交给模型”更可控。
