# Deep Read｜固定知识片段顺序、限制 Token 与模拟多段聊天

> 来源：`output/20261025__16 LLM性能优化 02_ev/content.md`（8分10秒），Deep Read V6.4。

本节继续上一段客服性能优化。讲者首先提出**让 RAG 返回的 Top-N 片段顺序稳定**。例如用户问“我大专可以学吗”和“我专科可以学吗”，意思相近，可能召回同样三条资料 A、B、C，但检索得分细微变化会导致排序不同。讲者建议在最后阶段按首字母或数据库 ID 固定顺序，以提高前缀缓存命中。

他认为只要最后三条都送给 LLM，排列顺序不会影响模型答复，因此可以忽略三条之间的得分差异。这是其推导中较强的假定；原文没有对此做对照实验。

随后介绍**Temperature**：意图识别建议设为 0，强调稳定和少创意；客服回复可以设为 0.3，兼顾一定自然表达与可控性。再谈**输出长度**：在系统提示词里要求回复不超过 200 字，同时设置 `max_tokens` 硬性上限，减少不必要的生成时间。

课程最后介绍**多段回复**。讲者希望客服像真实聊天一样分几条短消息，但不必对每条消息重复调用 LLM；可以一次生成含换行符或分隔符的完整结果，由后端按段落多次向前端推送 SSE 消息，从交互体验上模拟多次答复。

随后他又回到流式文本与 TTS：边拿到文本边合成语音，有助于缩短用户听到声音的等待。这里既有模型计算优化，也有界面体感优化，不能归为同一个指标。
