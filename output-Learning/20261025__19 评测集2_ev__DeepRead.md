# Deep Read｜评测客服回复时，讲者为什么先稳定意图与提示词，再看检索？

> 来源：`output/20261025__19 评测集2_ev/content.md`（8分36秒）。遵循 SenseWright Deep Read V6.4。

延续前节“输入—RAG—输出”三元组，讲者进一步追问：客服最终回复不准确，系统中哪些环节最值得先控制？

他先讨论**系统提示词**，认为其中有比较固定的助手身份、回复态度、长度要求和销售策略。比如用户直接问价格，销售流程可以规定先解释产品价值再引导客户留下联系方式。讲者把这些规则视为系统行为的一部分，而不仅是文案润色。

然后他将**意图识别**从系统提示词中单独抽出来，理由是意图识别承担独立的任务：分析用户现在问的是什么商品、应该查询什么资料、是否需要 Query 改写，以及下一步回复文字、图片还是视频。讲者用轻量模型完成这一步，最后把流程明确为：

**用户提问 → 意图识别/Query 改写 → RAG 检索 → 客服大模型结合系统提示生成回答 → 返回用户。**

随后进入核心判断：系统提示词和意图识别逻辑在初期开发调试后通常变化不大，知识库内容却可能频繁更新、规模也更大。因此当客服效果逐渐变化时，讲者希望优先关注 RAG 检索阶段的命中与召回情况。

他的评测策略是**先把相对稳定的规则和意图识别调通，再建立黄金数据集测 RAG**。这是为了减少同时调整多个变量而无法判断错因。视频到此结束，没有具体给出自动化评测脚本。
