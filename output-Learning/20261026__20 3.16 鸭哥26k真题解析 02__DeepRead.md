## 第一部分：AI 客服转人工遇到峰值流量

讲师没有只谈服务器扩容，而是从客服业务队列着手。他设想用户不断发起转人工请求、接待席位有限，于是需要决定谁先服务、等多久、系统超载时做什么。给出的机制包括：按照问题紧急程度或商业价值分级；等待时间越长优先级越高，以避免低优先级用户永远排不到；人数过多则改成留言回电模式；给出预计等待时间；轮到客户时通过消息提醒。

他还提出让 AI 在转交时带上对话摘要、常用回复和工单初稿，减少人工重新理解问题的时间。峰值保护措施则包括限制入口、要求先提供订单号或问题类型、熔断部分路径。这里同时讨论了排队算法、体验管理、人工效率及资源保护；其中“售后最不紧急”等表述只是讲师举例，并非可直接照搬的服务准则。

## 第二部分：多个 Agent 的“全局启动”究竟是什么

后半段的问题是“分布式环境下如何启动全局 state / 多个 Agent”。讲师先质疑这个需求是否清晰：如果 A→B→C→D 串行执行，用顺序 API 调用即可；如果四个 Agent 并行协作，则不仅需要同时运行，还要维护全局任务状态、跨服务拓扑和中断恢复。

他拆出几个相互依赖的要素：统一的任务 ID；外部状态存储（例如 Postgres checkpoint）；多个执行节点的分配和消息通知；图/流程拓扑连接；共享状态写入时的并发控制；某个节点失败后的定位与恢复。Redis 分布式锁仅能约束部分竞争写入，不能解决任务路径、事件丢失或多个 checkpoint 如何拼接的问题。

## 第三部分：复杂度与收益之间的权衡

讲师倾向让业务流程保持串行，认为多数业务不必为了并行而引入复杂的分布式状态协调。材料将“多个 Agent 可并行”与“跨服务工作流编排”有时混在一起，并对行业产品能力作了没有系统核实的断言。其核心意图仍是：先问清楚是否需要共享可变状态，再讨论用什么基础设施。

最后一个简短答疑涉及按租户或会员等级切换模型，讲师视其为业务规则分支，示例中用简单条件判断实现。
