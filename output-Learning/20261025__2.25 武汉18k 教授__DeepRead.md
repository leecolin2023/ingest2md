# Deep Read｜文旅 Agent 的多章节报告，审批权究竟在 Prompt 还是系统状态？

> 原始材料：output/20261025__2.25 武汉18k 教授/content.md（39分19秒）。Deep Read V6.4，Coverage-Preserving；材料是面试对话及直播复盘，存在自动转写错词。

## 从个人经历到技术主张

应聘者先介绍跨境电商项目：AI 客服结合 RTC、ASR、RAG、TTS 提供语音问答，也谈了销售聊天清洗、模型微调、文案和图片运营。面试官有自己的聊天服务经验，注意到实时语音模型的延迟和微调成本。双方讨论了基座模型升级会使原有微调结果迅速落后，面试官更倾向先利用已有模型并以外部知识补充业务能力。

## 面试官真正的问题是什么

面试官正在设计文旅场景 Agent：景区用户注册并录入运营资料，系统基于行业专家知识组织活动策划或经营诊断。最终输出是一份多章节的专业文档，用户能够逐章补充背景、反复修订、选择版本、同意后再进入下一章。

他的难题不是简单出现一个“下一步”按钮：**用户在当前章节的开放聊天框里可以输入任何文字**，甚至说“直接进入下一章”。系统如何保证未经正式确认就绝不推进？此外，用户可能回退到此前章节，修改之后又影响后续产物。面试官要求解释这一规则如何由协议和程序保证，而不是仅靠 Prompt 说“不要前进”。

## 应聘者提供的方案与双方分歧

应聘者很快回答 LangGraph 的 interrupt 与 Checkpoint 就能实现，举例在节点中断后弹出“批准/拒绝”按钮，批准后 resume 继续。面试官反复指出：这个回答没有解释开放文本输入与批准状态如何隔离，也没有给出实际可复现代码或状态机。他关心的是**控制权在模型生成的文字里，还是在系统的明确业务状态里**。

应聘者坚持问题百分之百由 interrupt 解决，把多章节比作游戏关卡，反复举按钮和中断的例子；面试官仍要求具体说明，双方对问题边界存在持续误解。

随后双方谈 Skill、流程规则与确定性编排。应聘者建议把场地容量、经费和规划步骤写成节点及条件判断；面试官强调需要从真实行业业务中定义规则。通话结束后，讲者在直播中抱怨对方过度追问、没有读 LangChain 文档。

## 这次面试留下的关键问题

**中断机制是一种执行工具，不等于完整的审批协议。** 原文中面试官反复问的其实是：状态如何记录、批准命令如何鉴权、普通文本怎样不能触发敏感状态变化、历史章节修改后下游怎样失效。应聘者强调了技术名词，却没有把上述保证落实到事件和状态转换。
