# Deep Read｜讲者怎样从简历中的“性能优化”回到真实客服链路

> 来源：`output/20261025__15 LLM性能优化 01_ev/content.md`（8分12秒）。Deep Read V6.4，保留作者主张及现场修正。

讲者首先批评简历上一句“兼顾语义与专有名词命中率、检索性能提升四倍”等描述过于空泛，认为应回到前面讲过的混合检索、Top-K/Top-N、Rerank 等具体机制回答，而不是把没有解释的倍数当作亮点。

之后，他列出客服链路性能优化的多个抓手：提示词/前缀缓存（Prompt Cache、KV Cache）、意图识别与客服回复的模型选型、关闭不必要的深度推理、知识库与系统提示词的风格一致、提示词结构与固定前缀，以及限制输出长度和使用流式输出等。

**提示词前缀缓存**是本节的主线。讲者提出把“固定内容—不常变化内容—频繁变化内容”依次排列，使多次请求能够重用相同的前部上下文。他还建议把系统提示词尽量合并，担心过多消息块导致缓存不能命中。这属于对特定服务商机制的口头判断，视频没有列出 API 版本及实测。

在**模型选型**上，他主张简单的意图识别使用成本低的轻量模型，商品客服的常见回复使用速度较快的模型，而不是所有请求都使用最昂贵的旗舰模型；对于脚本化客服，他建议关闭深度思考。

他还讨论文本风格：如果系统要表现为热情导购，知识库话术却冷漠，可能导致回答风格割裂。最后有一个现场修正：起初认为 RTC 语音链路不需要流式输出，随后想到可以边生成文本边进行 TTS，于是认可流式链路的潜在价值。

本节不是完整的压测结果，而是讲者为面试整理的一组可讨论的性能优化策略。
