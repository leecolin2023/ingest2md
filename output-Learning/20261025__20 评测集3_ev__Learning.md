# Learning｜为什么检索 Recall@K 高，最终给模型的证据仍可能不对？

> 原稿：`output/20261025__20 评测集3_ev/content.md`，Learning V0.7.0；独立 Review 调用隔离未通过验证。

## 两个候选集合要分别评估

假设一个问题有三条必要证据 A、B、C。Top-K=15 召回了 A、B、C，说明候选覆盖良好。但重排后 Top-N=3 返回的是 A、D、E，那么模型只拿到了 A，B 与 C 被精排过程丢掉了。

因此**Top-K Recall** 与 **Top-N Recall / 命中覆盖**要分开测量。否则你可能只看到初排很好，却不知道最后上下文为何答不出用户的问题。

## 标准答案不应只是一段文本

对于需要多个证据的问答，黄金数据集应至少标记相关文档 ID、必要事实，以及可接受的回答条件。必要时还要注明“多个证据任取其一足以回答”还是“必须组合所有证据”。如果标注的是三条等价重复知识，就不能简单要求模型必须同时命中全部三条。

模型生成的措辞可以不同，但核心事实、否定关系、引用证据和业务操作仍应正确。因此**过程评测并不取代最终结果评测**，它帮助定位失败原因。

## 建立可回溯链路

每次评测保存 Query、路由与 SKU、初排 Top-K 的 ID 和分数、重排后 Top-N 的 ID、进入模型的实际 Prompt、生成结果。这样才能回答：“证据在哪里丢的？”是上游索引漏召、下游重排错排、上下文截断，还是模型拿到证据后仍答错？

目标是让一次“模型回答不准”变为具体可以复现的工程问题。
