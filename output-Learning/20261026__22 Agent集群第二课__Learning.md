# 什么是 MCP 服务平台，为什么多个 Agent 需要公共能力层？

> 从“Agent 集群第二课”提出的重复配置问题出发，按服务复用、协议接口与平台治理逐层解释。

## 一、先区分 MCP 协议、MCP Server 和集群

**MCP** 是让模型应用访问外部工具和资源的一套协议约定。**MCP Server** 暴露工具、资源和提示词等能力；**MCP Client/Host** 负责建立连接、发现能力并发起调用。多个 Server 形成企业的工具生态，不自动意味着高可用的“集群”，也不自动说明有多个智能体在协作。集群还需要部署副本、负载均衡、故障转移与运行治理。

有了标准协议，Agent 只需理解工具的能力声明和调用格式，减少为每个后端单独适配的代码，但底层鉴权、业务规则和数据权限仍然存在。

## 二、为什么一个企业会从项目内工具走向共享层？

假设客服 Agent、合同核验 Agent、销售 Agent 都要查同一个客户系统。如果每个项目各自维护数据库连接、权限、日志和异常处理，新增一项字段或修复一处漏洞需要同时改三个系统。统一的查询服务可以让三个 Agent 复用同一套数据访问规则，并集中控制审计行为。

复用的判据不是“有三个项目使用就一定共享”，而是接口是否稳定、访问权限是否能够隔离、升级是否可以独立进行，以及共享后的运维成本是否低于重复实现。

## 三、一条完整的调用链

用户提出查询→Host 判断需要工具→选择可访问的 MCP Server→Server 校验用户/应用身份和参数→执行数据库或业务 API→返回结构化结果→模型结合结果答复→系统记录调用状态与审计日志。

这里最重要的区别是：MCP 定义“怎么暴露并调用能力”，但不会凭空实现“业务数据正确、调用有权限、模型答案可信”。

## 四、平台化之后新增的四种治理负担

**身份与权限**：统一 API Key 只解决“谁来调用平台”，未必解决“这个用户能看哪些贷款合同”。需要把终端用户身份、租户、工具 scope 与业务权限传递到后端。

**可靠性**：共享 Server 失败可能影响多个应用，需要超时预算、断路器、重试幂等性、隔离池与多副本。读查询可以重试，支付、放款等写操作必须谨慎处理重复调用。

**可观测与成本**：应关联 request ID、trace ID、Agent、工具名、耗时、错误码、模型 token 与费用；否则不知道故障出在路由、Server、模型还是业务数据源。

**数据隔离与版本**：不同业务的知识库、长期记忆及提示词不应因“共享服务”被混用。版本发布需兼容旧客户端，必要时采用灰度。

## 五、什么时候不应该建平台？

如果只有一个简单 Agent，工具接口频繁变化，独立 MCP 平台可能增加网络跳转、部署维护与排障复杂度。可以先在应用内封装工具，等多个业务出现真实复用需求，再逐步抽离。**平台化的目的不是让架构图层次更多，而是在可控的共享成本下让重复接入、权限治理和运维更可靠。**
