## 自媒体 Agent 的业务背景

讲者把项目二定位为运营人员生成文章、封面、宣传图片或视频的工具，认为其适用于电商、教育、金融等不同公司。他建议面试时根据行业更换项目叙事、团队人员和个人职责，甚至明确说团队几个人可以自己编。这是课程中的包装话术，不是源稿提供的真实项目证明。

## 工作流为什么要拆成节点与子图

讲者认为运营内容生成通常经历选题、确定风格、生成草稿与图片、人工审核、修改直至通过。使用 LangGraph 可以将整体流程拆成可管理的节点，针对写作和绘图封装 Subgraph，再通过前端界面让运营提要求、选版本。

他强调 Human-in-the-loop：运行到人工确认时暂停，用户同意后才继续，拒绝则把修改意见送回相应生成节点。Checkpoint 保存中间状态，以便刷新页面、恢复对话或返回上一步。课程讨论了 PostgreSQL 作为状态存储，以及前端调用后端的恢复接口，但没有给出完整、可独立运行的实现。

## Prompt、API 和可靠性

讲者希望把平台相关 Prompt 模板集中管理，因为小红书、公众号、抖音等渠道的风格不同；还介绍 API 版本管理、图片生成服务抽离成 MCP 服务的设想。他承认部分计划需要年后才补充课程，不能当作已经交付。

可靠性环节包括 Python 上下文管理器记录 Token/耗时、备用模型、限流、重试、健康检查、Mock 开关和自动 API 文档；讲者提到 FastAPI 生命周期与 Python 模块拆分，让候选人能够解释为什么系统可以开发、上线与恢复。

## 为什么从运营 Agent 转到微调

后半段切换项目三。讲者先解释 RAG 与微调分别解决的对象：RAG 补充可变知识（价格、产品版本）；微调希望使模型长期遵循特定的销售沟通风格。再比较 SFT（示范对话）与 DPO（同一问题下优选/劣选回复），并说明销售聊天从数据中台清洗、人工审核后可生成两类训练样本。

训练策略上，他建议先用小模型、本地少量样本验证，再在云端训练更大底座。教学中混有如何编造项目经历与参数的建议，并未提供可核查训练数据、耗时或效果日志。

整段材料由**项目二工作流与工程治理**、**项目三 RAG/微调分工和训练数据**两条独立主题组成，不能混作一个已实施的系统能力清单。
