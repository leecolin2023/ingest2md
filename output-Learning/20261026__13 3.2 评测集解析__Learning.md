## 1. 评测首先是明确要检查什么，而不是先选一个库

假设一个自媒体 Agent 的工作流是：

`用户需求 →（可选 RAG 检索）→ 生成大纲 → 写文章 → 生成配图 → 人工审核`

它至少可能出现五种完全不同的错误：

1. 资料没找到：检索阶段漏掉了有用的素材；
2. 文案不忠实：资料写鞋子只有 45 码，文章却写有 42 码；
3. 文案不切题：用户让介绍卖点，系统却只介绍折扣；
4. 图片不符合需求：要求“猫在树上”，生成了“狗在树上”；
5. 流程走错了：没有查资料就开始写，反复调用无关工具，或者生成了结果仍遭人工打回。

这些错误的成因不同，因此需要不同的评测对象。**一个总分既不能告诉你哪里坏了，也很难指导下一轮改进。**

## 2. 对 RAG，先把“检索对不对”和“生成对不对”拆开

一次 RAG 调用至少有三个关键记录：`user_input`（用户问题）、`retrieved_contexts`（检索到的知识）和 `response`（生成答案）。为了评估答案正确性，最好再有人工确认的参考答案或参考事实。

Ragas 提供了多类指标，它们回答的问题不同：

| 评测对象 | 典型指标 | 要回答的问题 |
| --- | --- | --- |
| 检索 | Context Precision、Context Recall | 找回来的证据是否相关，关键证据有没有漏掉？ |
| 回答依据 | Faithfulness | 回答里的事实陈述是否受到检索上下文支持？ |
| 对题程度 | Response Relevancy | 回答是否真正针对用户的提问？ |
| 事实正确性 | Factual Correctness 等 | 回答是否符合可信参考答案？ |

例如“鞋子只有 45 码”，若模型回答“有 42 码”，就是忠实度问题。如果模型回答“活动打八折”，即便这句话来自知识库，对“卖点是什么”的问题仍可能不够相关。

但还要看检索源本身是否过期。**Faithfulness 高不等于事实一定正确**：如果检索出来的旧资料就有错误，生成模型忠实引用旧资料，仍会给用户一个错误答案。

参考：[Ragas 官方指标清单](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/)、[Faithfulness 定义](https://github.com/vibrantlabsai/ragas/blob/main/docs/concepts/metrics/available_metrics/faithfulness.md)。

## 3. 评测集怎样从零构建？

第一步，收集真实任务，而不是从模板随意编造几条“看起来正常”的问句。例如从客服、运营日志中收集“询问现价”“追问库存”“比较两款商品”“要求引用证据”“要求生成图片”等不同业务意图。

第二步，为每条任务建立可以检查的期望结果。对于事实问答，记录允许引用的知识版本、正确商品 ID、期望事实和必要的拒答条件；对于开放式文案，可制定品牌口径、必备卖点、禁用事实和人工验收标准。

第三步，标注关键证据。只存“问题—答案”不够定位检索错误，还应保存能够支持答案的源文档或片段 ID。这样才能计算 Recall@K，并区分“没找到”和“找到了却没用好”。

第四步，加入有代表性的难例：同义词、型号差一个字符、老旧资料、冲突证据、用户问题有歧义，以及上下文里存在不该泄露的信息。正常样例用于确定基线，难例用于暴露系统边界。

第五步，固定版本与切分，避免评测样本泄漏到提示词或被长期针对性调参。保留输入、知识版本、期望答案、实际输出、评分与失败原因，便于每次改动后做可比较的回归。

这套结构比“先收集 30 个问题，再让同一大模型打分”更接近可定位问题的工程评测。

## 4. 为什么 Ragas 分数不能代替人工标准答案？

LLM-as-Judge 的优势是可以大规模对开放文本做近似评价，但它也是一个模型判断，可能受到提示词、样本表述、评分尺度以及裁判模型本身的误差影响。

所以实践中需要把不同强度的检查结合起来：

- **确定性规则**：例如商品 ID、价格、金额、JSON 字段、权限标识，能比较就直接比较；
- **人工标注的参考事实**：解决“到底什么答案才正确”的问题；
- **自动语义评测**：发现忠实度、切题程度、表达质量问题；
- **人工抽检与 Bad Case 复盘**：纠正评分器误判，更新评测集。

评测库是工具，评测标准和样本设计才决定结论的价值。

## 5. 图片、工具轨迹、业务结果应该分别怎么测？

**图片评测。**CLIPScore 这类图文匹配指标用来评估图片和文字描述的语义对应程度；它不保证图片没有六根手指、文字没有拼错或所有业务约束都满足。Inception Score、FID 通常更适合从样本分布层面比较图像集合，不能单凭某张图片的 FID 判断“人是否长了六根手指”。对于局部事实错误，可考虑 VLM 判断或人工核验。课程把这些方法混讲了，学习时必须区分评价对象。

**轨迹评测。**如果 Agent 任务要求“先查最新价格，再生成商品介绍”，就可以记录实际工具调用，判断它有没有遗漏必需步骤、越过权限、重复调用、遇错不恢复。LangChain 的 AgentEvals 支持参考轨迹匹配，也支持用 LLM 评价整段轨迹。但并非所有合法任务都只有一条固定顺序：可以允许多条合理路径，避免把“步骤不同”误判为失败。

**业务评测。**文章是否被驳回、图片是否被重做、最终任务是否完成、用户是否转人工、P95 延迟能否满足要求，是实际使用结果。它们与模型分数互相补充：高文本质量分数不意味着客户满意，客户偶尔接受也不等于每一步安全。

参考：[AgentEvals 官方说明](https://github.com/langchain-ai/agentevals)、[LangSmith 轨迹与 Trace 说明](https://www.langchain.com/blog/langsmith-trajectories-tracing)。

## 6. 评测应该在什么时候运行？

评测有三个不同节奏：

**开发时**，每当切片、Embedding、检索规则、Prompt 或 Agent 工具流程变化，就运行一个较小但有代表性的回归集，尽快定位变化带来的效果差异。

**发布前**，运行稳定的版本化基线集，把明确不可接受的错误作为阻断条件，例如越权引用、捏造商品价格、错误执行重要工具。开放式指标不宜只凭一个自动评分决定是否上线。

**线上**，抽样脱敏后的真实请求，对低质量、失败或人工打回的调用回溯检索证据、模型回答和工具轨迹；用这些 Bad Case 逐步更新回归集。线上观察与离线评测应分开，避免同步评测显著拖慢用户请求。

课程提出“每天抽 100 条”只是一个示例，不是标准规模。实际应根据业务量、失败发生率、风险和成本决定样本策略。

## 7. 第三方模型不能修改，是否就不值得评测？

不应该直接得出这个结论。即便 ASR、TTS 或图片生成模型不可自行微调，评测仍可以用于**选择供应商、设置可用性边界、选择模型版本、制定人工兜底、识别高风险口音和场景**。能够优化的不只是模型权重，也包括整个业务流程。

不过，课程提醒的成本收益问题仍然成立：如果某项专用评测无法改变任何实际选择，投入优先级可以降低。正确的方法是先问“如果这个指标不合格，我们准备做什么”，而不是笼统地认为第三方模型不可修改就不用测。

## 8. 评测完成时我们真正应该得到什么？

不是一个漂亮的平均分，而是能够回答四件事：

- 哪类真实用户任务最容易失败？
- 失败发生在召回、生成、工具执行、媒体生成，还是业务流程？
- 本轮变更修复了哪些失败，又是否带来了新回归？
- 这些改进能否转化成任务完成、人工返工、合规风险或延迟的可观察变化？

如果以上关系已经说清楚，评测体系就不再是面试时用来罗列的技术名词，而成为持续改进 RAG 与 Agent 的具体工具。
