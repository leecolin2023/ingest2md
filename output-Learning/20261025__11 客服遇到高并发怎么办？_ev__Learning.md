# Learning｜高并发 RAG 客服如何分层减负，而不牺牲数据正确性？

> 原稿：`output/20261025__11 客服遇到高并发怎么办？_ev/content.md`。依据 Learning V0.7.0，尚无独立 Review 隔离验收记录。

## 首先辨别是哪一层成为瓶颈

客服请求常经历：意图识别 → SKU 过滤 → 检索 → 重排 → 生成 → 输出。高峰期用户量上涨，不代表每一层都需要水平扩容。应先观察各阶段 P95 延迟、QPS、RPM、模型 Token 用量和缓存命中率。

**过滤**能减少候选范围，但不减少意图模型的调用次数；**检索结果缓存**能减少重复检索和重排，却不必然减少生成调用；**完整答案缓存**可以省下生成，但必须处理价格、库存、个性化和权限等动态因素。

## Redis 缓存需要哪些边界

缓存键不能只存“问题的向量”。还需要考虑租户、SKU、知识库版本、用户权限、语言、检索配置等隔离维度。对于语义近似问题，必须设置足够严格的匹配门槛，避免把“可以退款吗”和“不可以退款吗”错认成同一种问法。

价格与库存最好从实时权威数据读取，不能因为 10 分钟缓存仍有效就返回旧价格。缓存过期时间和主动失效机制应与数据更新策略一起设计。

## RPM 与并发量不是一个概念

每分钟 2000 个请求，是**请求速率**，不是“一次能同时接住 2000 个活跃对话”的保证。还需要考虑平均请求耗时、Token 限额、并发连接数及上下游依赖。业务端能通过队列、限流、退避重试和合规扩容控制负载；使用多个账号绕过服务商额度不应作为默认可靠方案。

## 前端热门问题为什么能帮助系统

对热门、结果稳定、所有用户共用的问题，提供固定入口可以减少 Query 改写和检索的成本。若问题涉及实时促销或库存，应返回业务接口的最新值，而不是写死答案。

评估优化时可以分别做容量压测和正确性回归：缓存命中率提高了多少，用户可感知响应变快多少，有没有新增“串商品、串租户、过期事实”等风险。
