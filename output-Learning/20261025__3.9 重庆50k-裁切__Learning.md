# Learning｜跨境 RAG 客服为什么要同时考虑语言、检索和语音三层适配？

> 源稿：output/20261025__3.9 重庆50k-裁切/content.md。Learning V0.7.0；独立 Review 隔离未验证。

## 先识别失败发生在哪个环节

海外用户说一种小语种，系统可能在**ASR** 就识别错误，也可能 ASR 正确而 **Embedding** 模型无法把该语言与中文商品资料对齐，还可能检索正确但**生成模型**或 TTS 不支持该语言。三个问题不能统称“大模型不懂”。

## 一条可解释的多语言链路

用户语音 → 语言识别/ASR → 归一化查询 → 多语言 Embedding 或机器翻译 → 在有权限的商品知识中召回 → Rerank → 将证据交给支持目标语言的 LLM → TTS。

如果用户已经以文本输入，可以先排除 ASR/TTS 问题；若用户明确指定型号，先按 SKU 过滤，再做跨语言语义检索。

## 为什么不能盲目降维或固定 Chunk

只有数据规模、资源压力和评测结果才能支撑从 2048 维降至 1024 维的取舍。Chunk 也要考虑商品 QA 的事实边界，避免截断条件或价格更新时间。需要比较同一问题集上的 Recall@K、重排准确性和实际延迟，而不只是看向量变小了。

## 怎样评测

构造中文、英文与目标小语种的同义问句，标注对应商品和证据 ID。逐项检查 ASR 词错率、实体识别、检索覆盖、回答忠实度、响应语言及端到端时延。模型原本不支持某语种时，可以选择翻译中间层或支持该语种的供应商，而不是直接认定业务无法实现。

这场面试说明**语言覆盖是系统级设计，不只是生成模型的一个参数**。
