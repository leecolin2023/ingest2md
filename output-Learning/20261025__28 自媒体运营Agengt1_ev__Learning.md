# Learning｜LangGraph 的 Subgraph 和 Checkpoint 分别解决什么问题？

> 原稿：`output/20261025__28 自媒体运营Agengt1_ev/content.md`。Learning V0.7.0；独立 Review 执行隔离未验证。

## 为什么把一条 Agent 流程拆开

假设要为商品生成文案、图片、视频：三类任务共享商品 SKU、品牌风格和选题，却使用不同模型、输入约束、审核标准和错误处理。如果全部节点紧密耦合，修改图片生成逻辑可能破坏文字路径。

Subgraph 允许把特定业务能力封装为更小的工作流，再由主图进行编排。例如主图负责接收选题与生成任务，文案子图写标题和正文，图片子图生成与检查图，视频子图产出素材。它们通过明确定义的状态字段交换输入输出。

这种拆分首先服务**业务边界和可维护性**，不必因为团队刚好三个人就机械设计三个子图。若功能简单，单图更容易理解也完全合理。

## Checkpoint 保存的是什么

工作流的状态不仅是“已经走到第几步”，还可能包含当前 SKU、已批准的文案、待处理图片任务 ID、人工修改意见和下一步节点。Checkpoint 将这些状态持久化，使中断恢复、人工审批后续跑和历史状态回看成为可能。

但“有 Checkpoint”不自动意味着任意节点都能无副作用重放。涉及图片生成、支付或对外发布等有副作用的操作，要保存幂等键或已执行标识，避免恢复时重复计费和重复发布。

## 一个可验证的例子

用户批准一篇文案后，系统进入视频生成，外部服务暂时失败。好的工作流应能够恢复到视频任务，而不必重做已经批准的文案。可以通过实际关停进程、重启并恢复任务，检查状态和资源是否一致，而不是只凭配置文件存在就说“支持断点续跑”。
