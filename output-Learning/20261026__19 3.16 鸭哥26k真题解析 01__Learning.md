# RAG 商品知识库如何做到准实时更新，又不拖垮检索服务？

> 学习来源：鸭哥 26K 面试真题解析上篇。以“电商商品持续改价、上下架”为例，推导读写分离、增量同步与高并发保护。

## 一、先区分两个不同的变化

商品的语义内容，如品牌、分类、功能特点，需要参与文本检索和 embedding；商品的交易状态，如价格、库存、是否在售，可能每秒变化。如果把所有字段拼进一段文本重新向量化，任何价格改动都触发索引更新，系统成本随变更频率增长，而且检索结果在更新窗口内可能过期。

解决思路是让**语义索引负责找到商品候选，交易数据库负责给出当前可交易事实**。

## 二、一个可解释的查询流程

1. 业务数据库存完整商品事实，维护商品 ID、版本及更新时间。
2. 文本索引保存商品 ID 和相对稳定的商品描述。
3. 用户问“这双鞋多少钱”，检索返回一批商品 ID。
4. 用这些 ID 批量读取当前价格、库存、上架状态，过滤无效商品。
5. 重排剩余候选，形成包含当前字段和时间标记的模型上下文。
6. 生成答案前再次考虑价格等高时效字段是否需要强一致查询。

Redis 是加速查询的一种缓存选项，不应被描述成天然权威数据库。权威值应来自业务源系统；缓存应有 TTL、失效或版本比对机制。仅仅“不重启 Redis”不能保证持久性或数据不丢失。

## 三、CDC 与索引更新承担不同职责

CDC（Change Data Capture）读取数据库变更日志，通常经消息队列/消费者把更新传到搜索索引、缓存或下游分析系统。它可以降低源库与查询侧的直接耦合，但它是**异步链路**：存在延迟、重复消费、乱序、重试与死信。消费者需要按商品 ID 幂等更新，并依据版本或序列号拒绝旧事件回写。

若价格只在查询时读取，CDC 可以主要负责索引中影响检索的属性；若缓存价格，CDC 负责刷新，但应提供过期回源和失败告警。业务对“准实时”的要求，需要规定允许延迟，例如几秒或几十秒，而不是只有“实时”二字。

## 四、流量高峰再加一层容量治理

检索、交易字段读取、推理 API 的瓶颈可能不同。网关限流保护系统入口；缓存减少重复查询；批量读取降低 N+1 查询；异步队列适合可延期工作（如索引重建、批量生成），不应把所有要求立即响应的在线聊天请求一律塞入队列。模型层要做并发上限、超时预算、降级和熔断。

## 五、一个重要的正确性边界

“返回最相似商品”不等于“商品可售”。查询层必须把**检索相关性**与**库存/下架/价格真实性**分开校验。只有当索引版本、业务数据时间和用户操作权限都满足约束，RAG 的文本回答才可能成为可靠的业务辅助信息。
