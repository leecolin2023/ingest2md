意图识别，你自己说，哪一场挨进来的面试不问？只要面试官敢问 20K offer，你的这个回答你绝对没有听过，面试官更没有听过。哎，我说出来，你就是今天最靓的仔。不掏点干货，你们还以为我是颜值主播。首先，我们意图识别业内常见的方案有 4 种：1、2、3、4。第一种叫结构化 Function Call。什么意思？

我举个例子，哎，这玩意怎么看起来有点像工具调用啊？对呀，你没有听错，工具调用它就是意图识别的一种。假设你有两个工具，一个查天气，一个做菜，用户问：请帮我查一下北京今天的天气是什么？好，那大模型是不是就会在你塞给大模型上下文中的工具中去选择查天气？这叫不叫意图识别？

同时还会把参数填充给工具：北京、5月8号，然后工具返回今天的天气是什么？所以结构化就体现在大模型还会直接帮你把参数填充好。所以记住第一个结论，工具调用就是意图识别的一种。第二种方式：提示词分类。我举个例子，你要做个酒店 Agent。那酒店它有哪些能力啊？比如退房、订房，

洗衣、吃饭等等二十种。那客户问：请帮我订个房。所以这个时候大模型的上下文就有用户的提问——请帮我订个房，然后再加上所有的能力范围。你会把这些所有能力都塞给大模型，你告诉大模型：啊，我们的这个 Agent 有这么多的能力。然后它会意图识别出来，用户是想要订房，接下来去调用子 Agent。那也就是说我们的每一个……

子 Agent 分别对应一项能力，这也是业内非常通用的方案。我订房就走订房的 Agent，我退房就走退房的 Agent，这叫做路由。好，我们再来看第三种，叫 RAG 分类。RAG 分类一般用于什么场景呢？假设我们有一个非常大型的客服，很大很大的系统，跟淘宝一样大。那可能这个系统的能力范围非常广，有几百种。

怎么办？我还能用前面的这种方式吗？将所有的能力都塞给提示词吗？不可以吧？这上下文太长了。所以这个时候我们可以通过 RAG 检索。我举个例子，用户问：请帮我查一下这个订单，物流到哪里了。好，通过 RAG 的语义检索去召回相似度最高的 top K。好，剩下 3 条：一个订单查询、一个物流、一个数码 3C。

然后大模型去决策：哦，原来你是要查物流，然后去走物流 Agent 去查询这个订单的物流信息。到这里你发现没有？二和三，他在做什么事情呢？它既是意图识别，又是路由啊，所以意图识别和路由是两个概念，就跟你开车一样，要导航，我要去湖北省武汉市，我要去湖南长沙。

全国那么多城市，你哪里记得住呢？所以你先是一级的省份，二级的城市，三级的县城，那你跟这二和三是不是一样的？提示词分类它是属于一级路由，退房、订房、洗衣、吃饭叫一级啊，最后筛选出来，我们就是订房。那 RAG 分类呢，二级路由。你看我前面有几百种，我通过 RAG 检索去进行筛选，筛选之后只剩下几条相似度最高的，这叫二级。然后将……

二级路由筛选完的精简内容丢给大模型的上下文，这个时候上下文是不是就不会被撑爆了，最后返回用户的真实意图。所以二和三的明确定义，它叫意图识别加路由。我们再来看第四种叫模型微调。我们的意图识别，其实也可以单独去训练一个模型进行微调，微调提供哪些数据呢？全部都是这种数据，对啊，我要干个什么什么。

意图是什么啊？我要吃饭，意图是吃饭，我要洗澡，意图是洗澡，给大家的这种数据，让模型去训练，最后训练出一个专门用于意图识别的模型。那每次用户提问，先走我们的意图识别模型，得知用户意图之后再去调什么大模型进去。那什么情况下会用模型微调呢？其实它有它独特的优势。前三种方案它都需要干什么啊，都需要联网啊，如果说我们有些。
